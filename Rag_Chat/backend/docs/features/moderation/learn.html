01

TL;DR

읽는 데 60초
제일 위험한 것

키워드 매칭만으로는 PII·대외비 보호가 안 된다. "주민등록번호"란 단어가 들어있는지를 보는 것과, 실제 901101-1234567 같은 패턴을 잡는 것은 완전히 다른 일이다. 키워드 사전이 "보호 중"이라는 잘못된 안전감만 주고 진짜 PII는 통과시킨다.

글로벌이 합의한 정답

3종 세트 — sensitivity label · DLP rule · audit log. Microsoft Purview, Google Workspace, Slack Enterprise, Atlassian, Fasoo 전부 같은 구조. 셋 중 하나가 빠지면 무너진다.

Triple Chat 결정

3-layer label-based. Layer 1 = 업로드 시 라벨 부여, Layer 2 = retrieval에서 권한 vs 라벨 비교, Layer 3 = 입출력 모더레이션 (PII regex · 키워드 · 임베딩). 키워드/regex/embedding은 "도구"이지 "전략"이 아니다.

02

왜 이게 어려운가

개념 정립

"대외비"는 보안 등급의 중간 지대

공공 부문 정의 (파수 페이지 인용):

대외비 문서란 비밀(secret) 외에 직무 수행상 특별히 보호가 필요한 사항.

핵심은 "직무 수행상" 이다. 비밀은 금고에 넣고 안 꺼내면 되지만, 대외비는 써야 한다. 안 쓰면 업무가 안 돌아간다. 그래서:

트레이드오프

보안 ↔ 생산성. 너무 막으면 사용자가 우회한다 (개인 메일·Slack DM·메모장에 복붙). 이 균형을 어떻게 푸느냐가 회사마다 다르다.

LLM이 끼면 문제가 더 어려워진다

기존 DLP는 "사람이 파일을 첨부해서 외부로 보냈는지"만 본다. RAG는 4 군데에서 누설이 발생한다:

  1. 사용자가 자기 권한 안의 chunk만 검색해야 한다 → ACL 매칭
  2. LLM 답변이 권한 밖 chunk를 재구성 가능 → 출력 검사
  3. 사용자 질문 자체가 민감 정보를 LLM에 송출 → 입력 검사
  4. 외부 LLM에 보내는 raw context = 회사 밖으로 데이터 전송

→ 모더레이션 경계는 한 곳이 아니라 4 군데다 — 업로드 · 질문 · 검색결과 · 답변.

"그냥 금칙어 사전 두면 되지 않나요?"

이 접근이 첫 분기에 죽는 이유:

  • PII: 키워드 매칭은 실제 데이터 형식을 못 잡는다. 잡으려면 regex.
  • 대외비: 코드네임은 자주 바뀐다. 운영자가 코드 배포 권한이 없으면 죽은 사전이 된다 → DB-driven 운영자 UI 필수.
  • 맥락 의존: "원가"란 단어는 발표 자료에선 OK, 영업팀 답변에선 BLOCK. 단순 사전으론 표현 못 함 → boundary 분리 필요.
03

글로벌 패턴 한눈에

벤치마크
Fasoo · 한국 엔터프라이즈

Data-Centric DRM

철학: 보안은 네트워크/엔드포인트가 아니라 문서 자체에 박는다.
  • Cataloger AI로 자동 라벨링
  • DRM 암호화 — 파일이 자기 정책 들고 다님
  • FILM 추적 — 외부 PC에서도 사용 로그
  • AI-R DLP — GenAI 채널 별도 차단

우리에게 적용: 풀 DRM은 못 한다. 단 "라벨이 컨텐츠를 따라다닌다" 원칙은 chunk metadata로 재현 가능.

Microsoft Purview · 표준

Sensitivity Label

모든 컨텐츠에 4단계 라벨이 있고, 라벨이 정책을 결정한다.

Public → General → Confidential → Highly Confidential

// 정책 (라벨에 자동 매핑)
없음   워터마크    암호화+DLP        공유차단+보존

M365 Copilot 시그니쳐: 사용자 ACL을 그대로 LLM context에 전달. 사용자가 못 보는 파일은 Copilot도 못 본다.

Google Workspace · DLP

Predefined Detectors + Confidence

~150종 PII/금융/의료 정규식 사전 제공. confidence 점수(high/med/low)로 false positive 억제.
  • Luhn 알고리즘 → 신용카드 false positive ↓
  • Actions: block · warn · audit only (우리 BLOCK/MASK/WARN과 동일 매핑)
  • Gemini Workspace는 라벨 기반 retrieval 제한
Slack/Atlassian · 통합

Third-party DLP + 시각 차단

자체 안 짜고 Nightfall · BigID · Polymer 통합. 메시지 송신 직전 스캔, send 버튼이 회색으로 비활성화돼 사용자가 학습한다.

우리에게 적용: [수정됨·N건] ribbon으로 사용자에게 "무엇이 차단됐는지" 알려주는 UX = 같은 원칙. silent drop 금지.

Apple / Meta · 내부 코드네임

코드네임 자동 블랙리스트

모든 미공개 프로젝트에 코드네임 부여 (Apple "Titan", Meta "Quest"). 사내 모든 LLM·channel·메일에 동일 키워드 룰 상속. → Triple Chat의 ForbiddenWord(category="코드네임")가 이 패턴의 mini 버전.

왜 셋이 다 필요한가

라벨만 있고 권한 매칭 없으면 → 그냥 메타데이터 (보호 안 됨).

권한만 있고 라벨 없으면 → 매번 ad-hoc 키워드 매칭 = false negative 폭증.

추적 없으면 → 사고 사후 조사 불가능 + 운영자가 룰 튜닝 못 함.

06

Triple Chat 결정 · 3-layer label-based

핵심 설계
L1
인덱싱 (업로드 경계)
업로드 시 Document.sensitivity 라벨 부여 (사용자 선택 → phase 2에 자동분류). restricted는 vector store 진입 차단.
knowledge.Document.sensitivity · chunk metadata 상속
L2
검색 (retrieval 경계)
User.access_level ≥ chunk.sensitivity인 chunk만 반환. 필터된 결과는 citation ribbon에 [수정됨·N건] 가시화 — silent drop 금지.
chat.User.access_level · retrieval filter · citation badge
L3
입출력 검사 (질문·답변 경계)
PII = Presidio + 한국 regex. 대외비 키워드/regex = ModerationRule(확장된 ForbiddenWord). 답변에도 동일 적용 (outbound).
moderation.filter.apply() · pattern_type=KW/RE/EMB

왜 라벨이 첫 단추인가

라벨이 없으면 모든 layer가 ad-hoc 키워드 매칭에 의존하게 된다. 라벨이 있으면:

  • Layer 2는 단순 비교 — user.level >= chunk.level
  • Layer 3은 라벨에 따라 다른 룰셋 적용 (예: restricted 답변은 외부 LLM 차단)
  • 운영자는 라벨 단위로 정책 관리 → UI가 단순

왜 키워드/regex/embedding은 "도구"이지 "전략"이 아닌가

  • 키워드: 정확하지만 누락 많음 (변형·오타·동의어).
  • regex: 형식 고정 데이터(주민번호·전화) 강점, 자연어엔 약함.
  • embedding: 자연어 의미 잘 잡지만 비용·지연·해석 어려움.

→ 각각 특정 카테고리에서만 강함. 전체 전략은 라벨이 잡고, 각 layer가 알맞은 도구를 고른다.

거부한 옵션과 이유

옵션거부 이유
키워드 사전만 풍부히§ 02에서 다룸 — 잘못된 안전감

여권 비유 (Fasoo DRM 본질)

일반 파일 = 종이 메모. 복사하면 그만.
Fasoo DRM = 여권을 들고 다니는 파일. 어디로 가든 출입국 검사.
우리 chunk metadata = 여권 미니 버전. vector store에서 꺼낼 때마다 검사.

이중 자물쇠 비유 (4 boundary 이유)

한 자물쇠는 도구만 있으면 따짐. 자물쇠 4개를 다른 메커니즘으로 → 한 곳 뚫려도 나머지가 잡음.
업로드(물리잠금) · 질문(키확인) · 검색(지문) · 답변(망보는 사람).

공항 보안 비유 (PII Layer 3)

키워드 매칭 = "주민등록번호 가져왔어?"라고 묻기. 솔직한 사람만 잡힘.
Regex 매칭 = X-ray 스캐너. 어떻게 숨기든 형태로 잡힘.
→ 진짜 PII 보호는 X-ray 필수.

실습 노트

직접 만져보기

현재 ForbiddenWord 테이블 확인

docker compose exec backend python manage.py shell -c "
from moderation.models import ForbiddenWord
for w in ForbiddenWord.objects.all()[:10]:
    print(f'{w.severity:8s} {w.direction:8s} {w.category:10s} {w.word}')
"

관찰 포인트 — severity·direction·category·word 4축뿐. pattern_type·boundary 없음 → Phase A 마이그레이션 필요.

현재 PII 처리 한계 실험

docker compose exec backend python manage.py shell -c "
from moderation.filter import apply
from moderation.models import ModerationLog
# 키워드 매칭 (현재 동작)
print(apply('주민등록번호를 알려주세요', source=ModerationLog.Source.INBOUND))
# 실제 PII 데이터 (현재는 못 잡음 — 잘못된 안전감!)
print(apply('내 정보는 901101-1234567 이야', source=ModerationLog.Source.INBOUND))
"

→ 첫 줄은 잡히고 둘째 줄은 통과한다. 이게 § 02에서 말한 문제. Phase C에서 Presidio + regex로 해결.

한국 PII regex 직접 테스트

import re

patterns = {
    '주민번호': r'\b\d{6}[-]?[1-4]\d{6}\b',
    '휴대전화': r'\b01[016-9][-]?\d{3,4}[-]?\d{4}\b',
    '이메일':   r'\b[\w.+-]+@[\w-]+\.[\w.-]+\b',
    '신용카드': r'\b(?:\d[ -]?){13,19}\b',
}

text = '연락처는 010-1234-5678 / 901101-1234567 / kim@example.com'
for name, pat in patterns.items():
    hits = re.findall(pat, text)
    print(f'{name:8s}: {hits}')

연습 과제 — Luhn 알고리즘으로 신용카드 false positive 줄이기 (Google DLP가 쓰는 방식).

라벨 기반 retrieval 시뮬레이션

사용자: access_level = "internal"

chunk A: sensitivity = "public"        → 통과 ✓
chunk B: sensitivity = "internal"      → 통과 ✓
chunk C: sensitivity = "confidential"  → 차단 (citation에 [수정됨·1건])
chunk D: sensitivity = "restricted"    → 인덱스 진입 안 함 (Layer 1)

→ Layer 2 핵심 동작. 차단된 게 있다는 사실은 보여줘야 한다 (silent drop 금지).
