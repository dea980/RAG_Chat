# Chunk Size × Overlap A/B 실험

목적: production에 하드코딩된 `chunk_size=1000, chunk_overlap=200`이 영업팀 질문에 대해 합리적인 선택인지 평가하고, 향후 데이터 변경 시 동일한 방법으로 재실험할 수 있는 베이스라인을 남긴다.

## 셋업

- **데이터**: `backend/galaxy_s25_data.csv` (7개 모델 행)
- **평가 셋**: `backend/chat/tests/evals/dataset.jsonl` — 영업팀 시나리오 12문항 (가격/스펙/색상/카메라/디스플레이)
- **분할기**: `langchain.text_splitter.RecursiveCharacterTextSplitter` (production과 동일)
- **검색기**: BM25Okapi (`rank-bm25`) — Gemini 임베딩 호출 없이 chunk 전략만 비교할 수 있도록 오프라인 셋업 사용. 임베딩 절대값은 다르지만 chunk_size/overlap의 **상대적 영향**은 그대로 유지됨.
- **지표**: 질문별 expected_keywords 중 top-k chunk 합본 텍스트에 등장하는 비율의 평균 (recall@k).
- **재현**: `cd backend && ./venv/bin/python -m chat.tests.evals.run_chunk_ab --sizes ... --overlaps ... --k ...`

## 분석

1. **chunk_size ≥ 250부터는 CSV 한 행 전체가 한 chunk** — 분할이 일어나지 않으므로 chunk_size를 더 키우거나 overlap을 늘려도 결과가 동일하다 (recall@5 = 0.789). production의 1000/200 조합도 이 구간에 속한다.
2. **chunk_size = 150에서 recall이 0.789 → 0.833으로 개선**. 한 행을 두 조각으로 자르면서 BM25가 "모델명 + 스토리지" / "카메라 + 디스플레이"처럼 의미 단위가 더 잘 분리된 chunk를 top-k에 올릴 수 있게 된다.
3. **chunk_size = 80은 과분할로 recall 급락 (0.569)**. 모델명/색상/스토리지가 같은 chunk 안에 함께 있지 않으면 키워드 매칭이 깨진다 — 자소서에서 언급한 "chunk boundary가 맞지 않으면 프로덕트 정보가 잘려서 부정확한 답변" 현상이 정량적으로 확인됨. overlap=30을 주면 0.569 → 0.653으로 일부 회복.
4. **overlap의 한계 효용**. 현재 데이터(짧은 CSV 행)에서는 overlap을 늘려도 동일 chunk 경계가 같은 위치에 떨어져서 의미 있는 차이가 거의 없음. overlap은 "긴 단락이 chunk 경계에서 잘릴 때" 효과가 나타나는 파라미터.

## 결론 / 권장

- **현재 production (1000/200)**: recall@5 = 0.789. 안전하지만, 더 좋은 설정을 남겨두고 있음.
- **데이터셋 특성에 맞춘 권장값**: `chunk_size=150, overlap=30` 부근 — recall@5 0.833 (+0.044). 응답 길이가 약간 줄지만 retrieve가 더 정밀.
- **운영 전 점검**: 행이 늘어나면 행당 글자 수가 증가하고 sweet spot도 이동할 수 있음. CI에 `run_chunk_ab.py`를 1회/주 실행해 회귀를 감시할 것.

## 향후 과제

- Gemini 임베딩 기반에서도 같은 그리드 돌려 절대 점수 보강 (cost 때문에 일회성으로만 수행).
- recall 외 precision/MRR 추가 — 현재는 키워드 hit ratio만 측정.
- 평가셋에 **실제 영업팀이 보낸 질문 로그**를 추가해 시뮬레이션이 아닌 실측 기반으로 전환.
- 검수 자동화: 새 RAG 데이터가 업로드되면 평가셋에 대해 recall이 임계치 아래로 떨어질 때 Slack 알림 (자소서 "향후 과제"로 명시한 검수 자동화의 1차 구현).
