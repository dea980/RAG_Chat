Async Ingest vs Context Lightening

"맥락의 경량화" 라는 표현이 가리키는 두 갈래 — Redis/Celery 를 어디에 쓸 것인가 — 의 장단점과 결정 기준.

⚠️ 갱신 결론 (2026-05-27)

지금은 둘 다 필요 없음. 이전 결론("A 인제스천 비동기 먼저") 은 과한 권고였다. 현재 ingest 는 CLI 단일 호출이라 HTTP timeout·동시성·외부 트리거 같은 진짜 압력이 없다. Phase 2 manifest (Django 모델 + SHA256) 만 들어가면 중복 적재·재실행 안전성 90% 가 해결된다. Celery 는 Phase 8 (Upload API) 에서 같이. B(컨텍스트 캐시) 는 트래픽 누적 후 임베딩 캐시만 단순히 추가.

아래 카드들은 그 시점이 왔을 때 참고할 설계 로 보존.

1. 두 갈래의 정의

갈래해결하는 문제Redis 의 역할Celery 의 역할
A. 인제스천 부하 분리 PDF/OCR/HWP 처리가 무거워 동기 호출이 timeout/UX 막힘 + 중복 적재 브로커, in-progress 락, 진행률 캐시 shared_task 로 ingest 비동기 실행, beat 로 디렉토리 정기 스캔
B. LLM 컨텍스트 절약 retrieval 결과·임베딩·대화 history 가 LLM 호출 비용·지연을 키움 retrieval 결과 캐시, 임베딩 캐시, 대화 요약 캐시 (거의 안 씀 — 캐시는 동기성)

2. 카드별 장단점

A · Ingest 측

인제스천을 Celery + Redis 로 비동기화

대상: chat.ingest.pipeline.ingest_path 호출 경로.

장점

  • HTTP/CLI 가 즉시 반환 — UX 막힘 해소
  • 이미 Celery worker + beat 가 떠 있어서 추가 인프라 ✕
  • Redis 락으로 같은 파일 동시 ingest 차단 (현재 88청크 누적 문제의 부분 해결)
  • Beat 스케줄로 NAS/S3 디렉토리 자동 색인 가능
  • OCR/HWP 처럼 분 단위 걸리는 작업이 워크플로우 막지 않음
  • 실패 시 retry / 재시도 정책을 task 단위로 관리 가능

단점

  • 로컬 dev 마찰 — worker 안 띄우면 task 실행 안 됨 (CLI 동기 경로는 유지 필요)
  • 관측성 — task_id 별 추적 위해 Flower / Sentry 도입 필요
  • 임베딩 provider 다운 시 retry 폭주 → 큐 폭주. backoff/DLQ 설계 필요
  • 락 만료 corner case — worker 가 죽으면 lock 이 영구 잡혀 차단되는 시나리오 (manifest 가 같이 가야 안전)
  • 테스트 복잡도 — CELERY_TASK_ALWAYS_EAGER eager 모드 분기 관리
B · Retrieval / LLM 측

Redis 캐시로 LLM 입력 컨텍스트 가볍게

대상: RAGUtils.get_rag_context + LLM 호출 전후.

장점

  • 임베딩 API 호출 캐시 → 비용 절감 (반복 질문에서 효과 큼)
  • retrieval 결과 캐시 → top-k 검색 자체를 건너뛰어 지연 감소
  • 대화 요약 캐시 → 멀티턴 컨텍스트 부풀음 억제 (7강 강사의 "히스토리 관리 핵심 과제")
  • 코드 변경 작음 — `cache.get_or_set` 한 줄
  • 비용·지연 효과가 즉시 측정 가능 (캐시 hit rate)

단점

  • 인제스천 병목은 그대로 — ingest 무거운 문제는 해결 X
  • retrieval 캐시는 stale 위험 — corpus 갱신 시 invalidation 정책 필요
  • 임베딩 캐시는 모델 바뀌면 통째로 무효 (model 키 포함 필요)
  • 대화 요약 캐시는 결국 또 다른 LLM 호출 → 비용 측정 필요
  • "맥락 경량화" 라는 단어가 가리키는 게 맞는지 모호 (Ingest 부하라면 헛짚는 셈)

5. 권장 결론 (갱신)

지금은 둘 다 보류. 대신 Phase 2 manifest 부터.

왜 A 도 보류인가

이전 권고는 트리거가 없는 상태에서 인프라를 미리 깔자는 제안이었다. 사실 관계:

  • 현재 ingest 는 python manage.py build_vectors CLI 단발성 호출. HTTP timeout 같은 압력이 없음.
  • 중복 적재(현재 88청크 누적) 는 Celery 락이 아닌 Django 모델 + SHA256 으로 해결됨.
  • PDF/HWP/OCR 무겁다 → CLI 면 그냥 기다리면 됨. request-path 가 아님.
  • Upload API 도 디렉토리 자동 스캔도 지금 요구사항 아님.

Celery 가 진짜로 필요한 트리거

  • Upload API — 영업팀이 Admin 에서 파일 드롭 → HTTP 응답이 ingest 못 기다림
  • 외부 트리거 — Slack/Email/Webhook 자동 인입
  • 동시 운영자 — 다수 사용자 동시 업로드

이 셋 중 하나라도 발생하는 시점에 위 카드 A 의 설계를 적용. 그전에는 동기 CLI 유지.

B (컨텍스트 캐시) 는

트래픽 누적 후 측정 데이터를 보면서 결정. 예외 — 임베딩 캐시 한 줄 은 비용 효과 즉각적이라 트래픽 없어도 도입 가능. 그 외 retrieval/대화 요약 캐시는 stale 위험만 키움.

지금 실제로 할 것

  1. Phase 2 — IngestManifest 모델 + SHA256 dedup (Celery 없이 동기로)
  2. Phase 3~7 — loader 추가 (Codex/다른 Claude 분담)
  3. Phase 8 가 오면 그때 이 문서 재방문
