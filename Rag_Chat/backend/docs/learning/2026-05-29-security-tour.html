1한 줄 요약

Triple Chat 는 비밀번호를 평문 저장하지 않고 PBKDF2 해시로 저장한다 (Django 기본). 사용자는 /auth/login/ 한 번 호출 후 받은 sessionid 쿠키로 다음 요청들을 인증한다. 비밀(SECRET_KEY · API 키 · DB 비밀번호)은 모두 .env 에 있고 .gitignore 로 git 에서 빠진다. CORS allowlist 와 CSRF 미들웨어로 다른 origin 의 무단 호출을 막는다.

핵심 결론 — dev 환경에서는 다 안전 설정. 다만 prod 로 갈 때 4 가지 추가 잠금 (HTTPS 전용 쿠키, 강한 SECRET_KEY 강제, 하드코딩된 dev 비밀번호 제거, ALLOWED_HOSTS 좁히기) 이 필요.

2비유 — 회사 출입증

회사 정문 + 카드키 시스템과 똑같다.
  • 비밀번호 = 입사 시 등록한 지문. 본인이 누른 손가락 모양 자체는 회사에 안 남는다. 대신 그 모양을 산수로 변형(=해시)한 결과만 남고, 다음에 손가락 댈 때마다 같은 산수로 비교한다. 회사 데이터가 털려도 원본 지문은 복원 불가.
  • 로그인 = 정문에서 지문 한 번 → 일회용 카드키(=sessionid 쿠키) 발급. 그 후 24h 동안은 카드만 대도 통과.
  • SECRET_KEY = 카드키 자체를 발급할 때 쓰는 본사 마스터 도장. 이게 새면 누구나 가짜 카드를 만들 수 있어서 회사가 망함.
  • .env = 마스터 도장 보관 금고. 사진(=git)에 절대 안 찍힌다.
  • CORS allowlist = 정문이 받아주는 "어느 건물에서 온 사람"인지의 명단. 다른 회사 건물에서 온 카드는 정문이 거부.

3비밀번호 저장 (PBKDF2)

Django 의 AbstractBaseUser 가 set_password() 를 호출하면 자동으로 PBKDF2-SHA256 해시를 만든다. DB 의 password 칼럼에 들어가는 값은 이렇게 생겼다: 

pbkdf2_sha256$600000$randomsalt$AbCdEfGh+long+base64+hash...
구간의미
pbkdf2_sha256해시 알고리즘 이름
600000해시 반복 횟수 — GPU 공격 비용을 60만배 높임
randomsalt사용자마다 다른 16자 무작위 — 같은 비밀번호도 다르게 저장됨 (레인보우 테이블 방어)
마지막 base64실제 해시 결과

관련 코드: Rag_Chat/backend/chat/models.py:25 의 user.set_password(password) 한 줄. 로그인 시점에는 user.check_password(input) 로 비교 (timing-safe — 매번 같은 시간 걸려서 응답 시간으로 비밀번호 추측 불가).

✓ 좋음: 평문 저장 0건. 우리 코드는 비밀번호 원본을 어디에도 안 들고 다님. 받자마자 set_password 로 해시.

4로그인 흐름과 sessionid 쿠키

1. 사용자: POST /api/v1/triple/auth/login/  {email, password}
   ─────────────────────────────────────────────────────────────▶
2. Django: User.objects.get(email=...)
          → check_password(password)   [✓ 일치]
          → login(request, user)
          → 응답에 Set-Cookie: sessionid=abc123...; HttpOnly; SameSite=Lax
   ◀─────────────────────────────────────────────────────────────
3. 브라우저: 그 쿠키를 자동 보관

4. 다음 모든 요청:  GET /api/v1/triple/moderation/rules/
                    Cookie: sessionid=abc123...
   ─────────────────────────────────────────────────────────────▶
5. Django: sessionid 로 user 조회 → request.user 채움 → DRF 가 인가

핵심 코드: chat/auth_views.py 의 LoginAPIView. Django 의 표준 authenticate() + login() 만 호출. 직접 쿠키 만지지 않음.

✓ HttpOnly 쿠키 (JavaScript 가 못 읽음 → XSS 로 쿠키 탈취 불가).
✓ SameSite=Lax (다른 사이트 클릭으로 발생하는 cross-site 요청에 쿠키 자동 첨부 안 됨 → CSRF 보호 강화).
✓ DB-backed session (Django 기본) — 서버가 강제로 sessionid 무효화 가능.

5.env 와 SECRET_KEY

민감 값은 모두 환경변수에서 읽는다. 코드에 직접 안 박힘. 

Rag_Chat/.env  (git 에 안 올라감)
─────────────────────────────────
DJANGO_SECRET_KEY=...
POSTGRES_PASSWORD=...
OPENROUTER_API_KEY=...
GOOGLE_API_KEY=...
QWEN_API_KEY=...
HUGGINGFACE_API_KEY=...

Rag_Chat/.gitignore 24, 69, 70, 71 행이 .env, .env.example, .env.local, .env.*.local 을 막는다. git status 에서 .env 가 절대 untracked 로도 안 나옴.

settings.py:38-52 가 SECRET_KEY 처리: 

SECRET_KEY = os.getenv(
    "DJANGO_SECRET_KEY",
    "django-insecure-n#&9eyax6nle6pk*6(!0hnvi-g4-+c-#ps&=*%5wn++dzvdlw8",
)

DEBUG = os.getenv("DEBUG", "1") not in ("0", "false", "False", "")

if not DEBUG and SECRET_KEY.startswith("django-insecure-"):
    raise RuntimeError(
        "DEBUG=0 requires a non-default DJANGO_SECRET_KEY. ..."
    )
✓ 안전망 한 줄: DEBUG=0 (=prod) 인데 SECRET_KEY 가 dev 기본값이면 서버가 부팅을 거부한다. "운영자가 깜빡하고 그대로 배포" 사고를 방지.

6CSRF / CORS — 다른 origin 차단

CSRF (Cross-Site Request Forgery)

악성 사이트가 사용자 브라우저로 "은행 송금 양식" 같은 걸 몰래 보내는 공격. Django 의 CsrfViewMiddleware (settings.py:115 행) 가 모든 POST/PUT/DELETE 에 CSRF 토큰을 요구해서 차단. 우리 코드엔 @csrf_exempt 가 한 곳도 없음 — 풀린 곳 없음.

CORS (Cross-Origin Resource Sharing)

Streamlit (http://localhost:8501) 과 Django (http://localhost:8000) 는 다른 origin. 그냥 두면 브라우저가 쿠키를 안 보낸다. 그래서: 

CORS_ALLOWED_ORIGINS = [
    "http://localhost:8501",   # Streamlit
    "http://localhost:3000",   # 미래 Next.js
]
CORS_ALLOW_CREDENTIALS = True
✓ allowlist 방식. 등록된 origin 만 쿠키 전송 허용. 다른 사이트가 Triple Chat 백엔드에 요청해도 브라우저가 쿠키 첨부 거부.

7현재 상태 점수표

항목 현재 설명

쿠키 Secure (HTTPS only)dev 만 OK 현재 미설정 → HTTP 도 허용. prod 에선 켜야 함.

8dev → prod 가기 전 체크리스트

지금 dev 상태로는 안전. 외부에 노출하려면 아래 4 가지를 settings 에 추가해야 함: 
# settings.py — prod 추가
if not DEBUG:
    SESSION_COOKIE_SECURE = True   # HTTPS 에서만 쿠키 전송
    CSRF_COOKIE_SECURE = True
    SECURE_SSL_REDIRECT = True     # HTTP 접근을 HTTPS 로 강제 리다이렉트
    SECURE_HSTS_SECONDS = 31536000 # 브라우저가 1년간 HTTPS 만 쓰도록 강제
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    SECURE_HSTS_PRELOAD = True

그리고:

  1. frontend/auth.py 의 render_login_form() 에서 value="user.internal@..." + value="Triple!23" 을 빈 문자열로.
  2. seed_test_users 는 DEBUG=False 일 때 자동 거부 (이미 구현되어 있음 — --force 없으면 막힘).
  3. ALLOWED_HOSTS 를 실제 도메인으로 좁히기 (예: triplechat.internal,api.triplechat.internal).
  4. CORS_ALLOWED_ORIGINS 도 실제 frontend 도메인만.

9연습 문제

1. 비밀번호가 정말 해시인지 직접 확인

cd Rag_Chat/backend
venv/bin/python manage.py shell -c "
from chat.models import User
u = User.objects.get(email='admin@triplechat.test')
print(u.password)
"

출력이 pbkdf2_sha256$600000$... 로 시작해야 한다. Triple!23 같은 평문이 보이면 어딘가 잘못된 것.

2. SECRET_KEY 부팅 안전망 시험

임시로 .env 의 DJANGO_SECRET_KEY 줄을 주석 처리하고 DEBUG=0 으로 띄워보라:

DEBUG=0 venv/bin/python manage.py runserver

"DEBUG=0 requires a non-default DJANGO_SECRET_KEY..." 에러로 거부되면 정상. .env 줄 다시 복구.

3. CSRF 보호 직접 확인

curl 로 sessionid 없이 chat 호출 → 403:

curl -i -X POST http://localhost:8000/api/v1/triple/chat/ \
  -H 'Content-Type: application/json' \
  -d '{"question":"test"}'

응답이 403 Forbidden 이어야 한다. 200 OK 가 오면 인증 게이트가 뚫린 것.

4. dev 기본값 제거 시뮬

frontend/auth.py 의 render_login_form() 에서 value="user.internal@..." 를 value="" 로 바꿔보고 Streamlit rerun. 로그인 화면이 빈 폼이어야 함. prod 직전에 해야 할 최소 변경.

5. 더 나아간 질문

brute-force 공격 — 누군가 /auth/login/ 에 비밀번호를 1초에 100번 시도하면 어떻게 막을까? 힌트: django-axes 또는 IP 기반 rate-limit (Redis 카운터). Phase D 후보.
