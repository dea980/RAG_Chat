⚠ 위험 — get_rag_context 가 stale pgvector 를 먼저 본다

현재 코드는 if VectorChunk.objects.exists(): pgvector path 패턴. pgvector 에 옛 데이터 (gemini 3072d) 가 있으면 그쪽이 우선. 그런데 query 는 ollama 768d 로 embed → dim mismatch 에러 → 빈 결과. production 에서는 Chroma fallback 도 안 가고 그냥 fail.

  • 해결책 A: pgvector 재인덱싱 (ollama 768d + audience_tier)
  • 해결책 B: pgvector 전부 wipe → Chroma only 운영
  • 해결책 C: 분기 명시 (env var USE_PGVECTOR=0 추가)

최선인가? — 솔직한 답

⚠ 부분적으로만. 인덱싱·ACL filter 골격 = 최선에 가까움. 운영 layer 미완성.

  • 잘된 것: namespace = tier 라는 단순 매핑 (가독성 + 운영). pipeline 에서 한 곳에서 tier 부여 (모든 sink 자동). internal_only 인덱싱 차단 (defense in depth). retrieval 단계에서 ACL filter 검증됨.
  • 덜 된 것 (구조적): persona 가 hardcode/fallback 만 — 사용자 실제 권한 반영 안 됨. ACL filter 가 동작해도 항상 P1 권한 (public+retail) 으로 떨어짐.
  • 위험한 것: Chroma vs pgvector drift. pgvector 가 먼저 호출되는데 옛 데이터. production 에서 dim mismatch → fail. 지금 즉시 해결 필요.
  • 데이터 측면: carrier tier 가 100% N/A scaffold — 영업 P4 외판이 챗봇 쓰면 "정보 없음" 만 받음. 실제 fetch 작업 필요 (sandbox 차단으로 처음 실패).
  • 측정 측면: IR 평가 dataset 이 60개 (author bias). 10K dataset 설계 문서만 작성됨, 실제 생성 안 함. 측정 없는 ACL 변경은 위험.
