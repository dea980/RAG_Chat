비유자동차 튜닝 다이노

엔진 출력 측정기를 안 달고 부품을 갈면 "느낌상 빨라진 것 같다" 가 한계다. 다이노 (dynamometer) 에 올려서 출력 곡선을 찍고, 부품 하나 갈 때마다 같은 조건에서 다시 찍어야 "이 부품이 +12hp 줬구나" 가 증명된다.

매핑. labeled QA dataset = 다이노. 거기 안 올리고 reranker, hybrid, 청크 변경 다 해봐야 "좋아진 것 같다" 까지가 한계.

PLAN6 단계 (ROI 순)

STAGE 0측정 — blocker, 다른 모든 단계의 전제

작업:

  1. backend/data/embedding_eval/sales_qa.yaml 작성 — 영업팀 실제 질문 30~50개.
  2. 각 질문에 정답 청크 식별자 라벨 (source_file + section).
  3. chat/embedding_eval.py (이미 untracked 에 존재) 에 mgmt cmd wiring.
  4. baseline 측정: MRR, Recall@5, Recall@10.

예시 dataset (5개):

- query: "Galaxy Z Fold6 가격 알려줘"
  expected_source: "data/samples/foldable_handbook.md"
  expected_section_contains: ["가격", "$1,899"]

- query: "Buds3 Pro ANC 되나"
  expected_source: "data/samples/buds_lineup.csv"
  expected_row_contains: ["Buds3 Pro", "ANC"]

- query: "Tab S10 Ultra DeX 무선"
  expected_source: "data/samples/tab_handbook.md"
  expected_section_contains: ["무선 DeX"]

- query: "A55 카메라 OIS"
  expected_source: "data/samples/a_series_handbook.md"
  expected_section_contains: ["OIS"]

- query: "S25 Ultra 무게"
  expected_source: "data/samples/galaxy_lineup.csv"
  expected_row_contains: ["Galaxy S25 Ultra", "Weight"]

비용: 2~3시간 · 완료 조건: baseline 숫자 1개 (e.g. MRR=0.42)

STAGE 1Reranker MRR +20~30%p

왜: single-lever 효과 최대. cross-encoder 가 query·doc 을 함께 보고 점수화 → bi-encoder 의 약점 보완.

작업:

  • .env 의 RERANKER_ENABLED=0 → RERANKER_ENABLED=1 토글
  • ONNX 모델 BAAI/bge-reranker-v2-m3 는 이미 repo 에 준비 (현 브랜치 = feature/onnx-reranker)
  • 파이프라인: dense top-20 → cross-encoder rerank → top-5
# chat/pipeline/modules.py — RetrievalModule
dense_hits = vector_store.similarity_search(query, k=20)
if RERANKER_ENABLED:
    reranked = reranker.rerank(query, dense_hits)  # ONNX cross-encoder
    return reranked[:5]
return dense_hits[:5]

비용: 1시간 (env 토글 + import + smoke test)

STAGE 2Hybrid 검색 (Dense + BM25) MRR +5~15%p

왜: dense embedding 은 "Galaxy A55" 같은 정확 명사 에 약하다. BM25 는 keyword 검색 — 정확 단어 일치에 강함.

작업:

  • pip install rank_bm25 (또는 langchain BM25Retriever)
  • ingest 시 BM25 인덱스 추가 빌드
  • 검색: dense top-20 + BM25 top-20 → RRF (Reciprocal Rank Fusion)
score(doc) = sum( 1 / (60 + rank_in_each_retriever) )

비용: 0.5 day

STAGE 3Category metadata + pre-filter MRR +5~10%p

왜: 현재 청크 메타에 product_category 없음. "태블릿 추천" 물으면 폰/버즈까지 섞임.

작업:

  • ingest 시 파일 경로에서 category 자동 부여: foldable_* → foldable, a_series_* → smartphone_midrange, tab_* → tablet, buds_*/watch_* → accessory, galaxy_* → smartphone_flagship
  • 검색 시 LLM 1콜로 쿼리 → category 추정 → chroma filter 적용 후 similarity
# chat/ingest/sinks/chroma.py — _to_lc_document
flat_meta["category"] = _infer_category(doc.source_file)

# retrieval
category = classify_query(query)            # 짧은 prompt → "tablet"
hits = vs.similarity_search(query, k=5,
                            filter={"category": category})

리스크: category 오분류 → false-negative. fallback (filter 없이 재검색) 권장. 비용: 0.5 day

STAGE 4청크 단위 정규화 MRR +0~5%p

현재 mixed:

  • lineup.csv row = ~50~100 토큰 (얇음)
  • handbook.md heading = ~200~1500 토큰 (들쭉날쭉)

청크 길이 편차 크면 embedding vector 가 같은 "밀도" 가 아니라서 cosine 비교 비정상.

작업: handbook heading 청크 800 토큰 넘는 건 sub-split. lineup csv row 는 얇으면 묶기 (또는 metadata 강화). 목표 ~300~500 토큰 균질.

비용: 1 day

STAGE 5Query rewriting / HyDE MRR +0~10%p

언제: 0~4 다 했는데도 MRR 부족할 때 마지막 카드.

  • Query rewriting: 짧은 한국어 쿼리 → LLM 확장 ("Z Fold6 얼마" → "Galaxy Z Fold6 시작가 launch price 출고가")
  • HyDE: LLM 이 가설 답변 생성 → 그 답변 embed → 검색. 짧은 쿼리 vs 긴 청크 거리 단축.

비용: 0.5 day. 리스크: 매 쿼리당 LLM 1콜 → 비싸고 느림.

STAGE 6코퍼스 품질 (지속)

  • caveat N/A 보완: Z Flip6 dimensions, Tab USD 가격, A16 칩셋 변형, Watch FE 충전 W
  • 사실 표현 통일: handbook 과 csv 가 같은 fact 다르게 쓰면 RAG 헷갈림
  • FAQ 청크 추가: 영업이 자주 받는 Q→A 쌍 자체를 청크화 (sales_faq.md)

EX연습 문제

문제 1 쉬움

baseline MRR = 0.42. reranker 켰더니 MRR = 0.61. 개선폭 (%p) 와 상대 개선률 (%) 둘 다 계산하라.

힌트. %p = 단순 차. 상대 = (new - old) / old × 100.

문제 2 중간

"Galaxy A55 카메라 OIS 지원?" 질문에 top-1 결과가 a_series_lineup.csv A55 행이지만 OIS 명시 없음. LLM 이 어떤 답을 할 위험이 있나? 어떻게 막을 수 있나? 두 개 이상의 layer 에서 답하라.

힌트. STAGE 6 (corpus 사실 표현 통일), STAGE 1~3 (reranker/handbook 청크 상위로), Korean prompt 의 "자료에 없으면 모른다고 답하라".

문제 3 어려움

1~6 모두 켜서 MRR oracle 대비 90% 도달. 그래도 영업팀 만족도 낮다. 어떤 차원의 문제가 남았을까? 3가지 이상.

힌트. retrieval 만 RAG 가 아님. generation 품질, corpus 누락, citation UX, latency.
