2026-05-29 Triple Chat / 보안 설계 관련: 페르소나 분석

같은 질문이라도 페르소나마다 다른 답이 나와야 한다. 매장직이 "기업 견적 얼마?" 라고 물으면 답이 없는 게 정답 이다. 본사 기획이 같은 질문 하면 공개 경쟁사 가격을 줘야 한다. 이걸 만들려면 인덱싱 / 검색 / 답변 / 감사 4 layer 모두에 페르소나 인식이 들어가야 한다. 기존 B1-B7 RBAC + Phase A SensitivityLabel 위에 1 layer 더.

RAG 특수 위험. LLM 이 chunk 들을 연결 해서 추론한다. chunk A = "S25 매장 KPI 목표 100대", chunk B = "현재 누적 50대" → LLM 이 "달성률 50%" 라 답함. 둘 다 따로는 OK 지만 합쳐서 매장 실적 누설. chunk 결합 추론이 가장 위험.

비유회사 출입증·캐비닛·CCTV

회사에 들어왔다고 모든 문서를 볼 수 있는 게 아니다:

  • 출입증 (badge) = 로그인. 누구인지 증명.
  • 부서 (department) = 페르소나. 어떤 데이터에 접근 가능한지.
  • 캐비닛 자물쇠 (lock) = chunk metadata. 데이터마다 누가 볼 수 있는지.
  • CCTV (audit log) = 누가 무엇을 시도했는지 기록.
핵심 — 자물쇠는 인덱싱 시점부터. 캐비닛 자체를 매장 사무실에 안 두는 게 가장 안전. 검색 필터·답변 마스킹은 보조 방어선.

신규로 추가할 것

  1. User.persona — DB migration. enum (P1, P2, P3, P4) + nullable (관리자)
  2. Chunk.audience_tier — ingest 시 부여. 파일 경로 매핑 + 운영자 override
  3. PersonaAccess 모델 — persona × tier 허용 매트릭스. admin 토글
  4. PersonaPolicy 모델 — prompt template, citation 형식, 답변 길이 상한
  5. EscalationAttempt — 권한 밖 정보 요청 로깅
  6. PersonaClassifier (선택) — 사용자 톤 분석. authorization 결정엔 X (정적 enum 우선)

5/L핵심 코드 5줄

chat/pipeline/modules.py — Retrieval ACL filter 확장:

# 기존 (Phase A)
filter = {"sensitivity_label": {"$in": allowed_labels}}
# 추가
filter["audience_tier"] = {"$in": tiers_for_persona(user.persona)}
hits = vs.similarity_search(query, k=20, filter=filter)
# Persona 매트릭스 위반 = retrieval 단계에서 차단. 답변 단계로 안 감.

chat/ingest/sinks/chroma.py — 인덱싱 시점 tier 부여:

flat_meta["audience_tier"] = infer_tier(doc.source_file)
# infer_tier: 파일 경로 → tier (예: samples/* → public, internal/* → internal_only)
# internal_only 면 인덱싱 자체를 skip 하는 게 더 안전

Query intent + persona match check tone = b2b vs User.persona = P1 → mismatch → EscalationAttempt 로깅

★33 신뢰성 원칙

1. 무성 드롭 금지

P1 이 B2B 정보 요청 시 "결과 없음" silent return X. 명시적 redirect:

"기업 도입 견적은 B2B 영업팀 담당입니다.
연락처: [redirect]
챗봇은 공개 가격만 제공할 수 있습니다."

2. 인덱싱 차단 > 검색 필터 > 답변 마스킹

L1 · 100% 안전

인덱싱 차단

chunk 가 corpus 에 들어오지 않음. 검색·답변 단계에서 만날 일 자체가 없음. internal_only 는 여기서.

L2 · 99% 안전

검색 필터

chroma filter 로 retrieval 단계에서 차단. filter 버그 가능성 1%.

L3 · 95% 안전

답변 마스킹

LLM 출력 토큰 검사. prompt injection 우회 가능성. 마지막 안전망.

3. 모든 escalation 시도는 audit

P1 이 "마진 알려줘" 시도 시:

  • 답변: redirect (위 1번)
  • audit: EscalationAttempt(user=p1_user, query="마진 알려줘", from_persona=P1, requested_tier=internal_only, decision=block, ts=...)
  • 운영자 대시보드에 누적 카운트. 패턴이면 운영자 룰 추가.

EX연습 문제

문제 1 쉬움

audience_tier=b2b chunk 100개. P1 매장 사용자가 "Knox" 검색. retrieval 단계 무슨 일? 답변에 무엇이 나와야?

힌트. filter 적용 후 hits=0. 무성 드롭 금지 원칙.

문제 2 중간

운영자가 admin 에서 "P1 도 carrier 정보 보이게" 토글. 진행 중 P1 세션 즉시 영향? 캐시·세션·DB 측면에서 답하라.

힌트. retrieval filter DB 매번 조회 / 세션 단위 캐시 / 채팅 모듈 즉시 무효화.

문제 3 어려움

P1 사용자가 5개 질문 연달아: "S25 카메라 스펙" / "S25 메모리" / "iPhone 16 카메라 비교" / "S25 마진율" / "S25 매장 KPI 달성률". 각각 어떤 layer 에서 어떤 결정? audit log 에 escalation_attempt 몇 건? 패턴이 운영자에게 무엇을 시사?

힌트. Q1-Q2 OK · Q3 = competitive (P1 권한 X) · Q4-Q5 = internal_only (corpus 외). escalation 3건 누적 = P1 사용자가 권한 밖 정보 자주 시도 패턴 알람.
