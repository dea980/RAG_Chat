## 2. 핵심 개념 — "문서 인덱스" 와 "벡터 인덱스" 는 같은 일을 한다

<div class="analogy">
<b>비유 — 도서관 카드 카탈로그</b><br>
종이책 도서관에서 책장은 책 본체. 카드 카탈로그는 "어디에 무엇이 있는지" 의 *지도*. 카드가 빠지면 책은 존재하지만 *찾을 수 없다* — 사실상 사라진 책.<br><br>
RAG 의 벡터 인덱스도 같다. 청크는 원본 텍스트. 인덱스는 "어느 벡터가 어느 청크냐" 의 지도. 인덱스에 없는 청크는 검색에서 *영영 등장 안 한다*.<br><br>
프로젝트 doc 도 똑같다. <code>_index.md</code> 에 등록 안 된 doc 는 사용자/AI 가 "이런 문서가 있다" 자체를 모름. <b>그림자 파일 (shadow file)</b> 이라고 부른다.
</div>

### 2.1 그림자 파일이 왜 위험한가

오늘 작업 직전 상황:
```
find Rag_Chat/backend/docs -name "*.md" | wc -l  →  46
_index.md 의 unique md 링크 수            →  43
                                              ↑↑↑
                                          3개 그림자
```

그림자 파일 3개 = `features/moderation/learn.md`, `features/moderation/references.md`, `features/night_autonomous/setup_learning.md`. 다음 agent (또는 사용자 본인) 가 `_index.md` 만 보고 "모더레이션 학습 자료" 를 찾으면 → 없다고 결론. 이미 만들어진 자료를 *다시 만드는* 비용 발생.

<div class="warn">
<b>주의 — RAG 와 동일한 함정</b><br>
청크를 임베딩만 하고 vector store 에 add 안 하면? 검색에서 안 나옴. 같은 청크를 *다시 임베딩* 하게 됨. 자원 낭비.<br>
오늘 같은 문서 등록 누락은 RAG 의 "임베딩 후 add 누락" 과 동일한 버그.
</div>

### 2.2 "Cross-link 무결성" = retrieval 의 reachability

RAG 의 검색은 *단일 hop* 이지만, 사용자가 "관련 문서" 를 따라가는 건 *다중 hop graph traversal*. 그래서 doc 간 cross-link 가 끊겨 있으면:

- 사용자가 doc A 를 찾았다
- doc A 끝의 "관련 문서" 가 doc B 를 가리킨다
- doc B 가 doc A 를 *역참조* 안 하면 → 사용자가 B → A 로 돌아가지 못함

대형 LLM 의 context window 에 비유하면: 한 청크에 *맥락* 이 없으면 모델이 "이게 무엇에 대한 글이지?" 부터 다시 추론. cross-link 가 그 맥락 역할.

오늘 검증한 결과: 5개 신규 doc 의 reachability ✓ (`_index.md` 에서 1-hop 으로 모두 도달). reverse 일부는 conceptual mismatch (시점 다름) 라 강제 안 함.

<div class="tip">
<b>핵심 — 강제와 의미의 분리</b><br>
"양방향 cross-link" 라는 규칙은 자동 강제가 의미 있는 부분 (구조적 reachability) 과 의미적 강제가 무의미한 부분 (시점 mismatch — 어젯밤 narrative 가 오늘 만든 문서를 *미래* 시점으로 참조할 수 없다) 을 구분해야 한다.<br><br>
RAG retrieval 도 마찬가지: top-k 가 클수록 무관한 청크가 섞임. 정확도와 recall 의 트레이드오프. 무조건 양방향이 답이 아니다.
</div>

## 3. 핵심 개념 — "Handoff doc" 은 LLM 의 KV cache 와 같다

LLM 추론 중 prompt 의 앞부분이 매번 재계산되지 않는 이유 = **KV cache**. 이미 계산한 attention 결과를 저장해 두고 다음 토큰 생성 때 *그 위에* 얹는다.

야간 4-agent 세션이 같은 구조다:

| LLM 추론 | 야간 세션 |
|---|---|
| KV cache | `handoff.md` |
| 다음 토큰 생성 | 다음 세션 (T1·T2·T3) |
| cache miss | handoff 가 stale → 다음 세션이 *전체 git log + 모든 doc* 을 다시 읽어야 함 |

오늘 T3 가 한 일 = **KV cache 를 다음 세션 시점으로 update**. handoff.md §13 신설, commit_split_plan.md 전면 재작성. 다음 세션이 `cd Rag_Chat && cat backend/docs/sessions/handoff.md` 하나로 5분 안에 진입 가능.

<div class="exercise">
<h4>연습</h4>
<ol>
<li><b>그림자 파일 찾기 연습.</b> 본 프로젝트 어디든 좋다. <code>find Rag_Chat -name "*.md" | wc -l</code> 와 가장 가까운 인덱스/카탈로그 파일의 entry 수를 세어보고 차이를 찾아내라. 3개 이상 mismatch 면 그림자 파일이 있다는 신호. 어떤 파일들이 missing 인지 적어보고, 그게 다른 agent (또는 본인) 가 만든 작업물인지 확인.</li>
<li><b>Cross-link reachability 실험.</b> <code>_index.md</code> 에서 출발해 `moderation/learn.md` 까지 도달하는 최단 경로 (몇 hop?). 그 다음 `moderation/learn.md` → `_index.md` 역방향 최단 경로는 몇 hop? 만약 직접 backlink 가 없다면 어떤 중간 doc 을 거치는지 그려보라. (RAG 의 reranker 가 multi-hop 추론을 못 하는 이유와 같은 그림이다.)</li>
</ol>
</div>

## 4. 핵심 개념 — "Commit 분할" 은 chunk size 와 같은 문제

RAG 의 chunk size 문제: 너무 작으면 context 부족, 너무 크면 retrieval 정확도 ↓. **하나의 청크가 하나의 의미 단위** 여야 함.

오늘 작성한 `commit_split_plan.md` 의 8 묶음:
1. chore 정리 (잡파일)
2. phase 5 OCR
3. phase 7-a HWP research
4. embedding lab
5. chunk_lab UI
6. moderation Phase A
7. design system
8. meta docs

**왜 8개로 쪼갰나** — 묶음 안의 모든 파일이 *하나의 의미* 를 공유. 누가 리뷰해도 "이 commit 은 X 를 함" 한 줄로 요약 가능. 만약 8개를 한 commit 으로 묶으면? 리뷰어 (또는 미래의 본인) 가 무엇이 어디서 왔는지 추적 불가 — `git blame` 이 의미 잃음.

같은 원리:
- 청크 = "검색 가능한 최소 의미 단위" → 표 한 개, 단락 한 개, 조항 한 개.
- commit = "되돌리기 가능한 최소 의미 단위" → 한 feature, 한 fix, 한 refactor.

<div class="tip">
<b>핵심 — `git revert` 와 RAG retrieval 의 공통점</b><br>
혼합된 commit 을 revert 하면 무관한 변경까지 되돌아감 (regression). 혼합된 청크를 검색하면 무관한 내용까지 LLM context 에 들어감 (hallucination). 둘 다 <b>"하나의 단위에 하나의 의미"</b> 원칙 위반의 결과.
</div>
