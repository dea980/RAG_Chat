### moderation/levels.py 신규 — sensitivity ladder + 헬퍼 함수
- **무엇을**: `Rag_Chat/backend/moderation/levels.py` 를 새로 만들고 세 함수 + 두 상수를 두었다. (`SENSITIVITY_LEVEL` dict, `DEFAULT_LEVEL="internal"`, `can_access(user, content)`, `should_index(level)`, `apply_acl_filter(hits, user_level)`.)
- **왜**: Phase A 의 1차 신호는 "라벨 한 줄". 라벨끼리 비교만 하면 끝나는 순수 함수를 ORM/Django 의존 없이 분리해 두어야, 4 boundary(업로드·질문·검색결과·답변) 가 모두 같은 ladder 를 공유한다. spec §3.2 "권한 매칭은 단조함수" 조항을 코드로 그대로 옮긴 것.
- **그때 상황**: 시작 시 `moderation/` 에는 `filter.py` (단방향 키워드 필터) + `models.py` (ForbiddenWord, ModerationLog) 만 있었음. ladder/ACL 개념이 코드에 한 줄도 없었다. spec/plan 문서는 이미 박혀있었지만, retrieval 함수(`chat/utils.py:RAGUtils.get_rag_context`) 는 chunk 의 메타데이터를 보지 않고 전체 결과를 그대로 반환하던 상태였다.
- **대안 & 선택 이유**: (a) `moderation/levels.py` 로 분리 — 채택. ORM 비의존 + 4 boundary 가 import 만 하면 끝남. (b) `moderation/filter.py` 안에 ladder 헬퍼를 두기 — 거절. filter.py 는 ForbiddenWord 패턴 매칭/로깅에 묶여 있어 ACL 까지 합치면 책임이 비대해진다. (c) `knowledge/models.py` 에 두기 — 거절. knowledge 는 데이터(Document·Department) 도메인, 권한 정책을 도메인 모델 옆에 두는 건 SRP 위반.
- **결과**:
  - 신규 파일: `Rag_Chat/backend/moderation/levels.py`
  - 검증: `python manage.py test moderation.tests.test_acl.AclLevelTest` → 5 ok / `ShouldIndexTest` → 2 ok / `RetrievalAclTest` → 4 ok

### knowledge.Document 신규 + Sensitivity TextChoices
- **무엇을**: `Rag_Chat/backend/knowledge/models.py` 에 `Sensitivity(TextChoices)` enum 과 `Document` 모델(`name`, `source_uri`, `sensitivity`, `sensitivity_set_by` FK→chat.User, `sensitivity_set_at`, `uploaded_at`) 을 추가.
- **왜**: spec §4.2 가 Document.sensitivity 를 Layer 1 의 1차 분류 신호로 못 박았다. 라벨이 메모리/JSON 만이 아니라 DB row 로 살아있어야 Django Admin 에서 운영자가 코드 변경 없이 수정 가능하다 (CLAUDE.md "관리자가 코드 없이 튜닝" 요구).
- **그때 상황**: 시작 시 knowledge 앱에는 Department·Contact·Product 만 있었음. "Document" 추상화 자체가 없었다 — 업로드 파일 추적은 `chat.IngestManifest` (sha256/source_uri 기반 dedup 용) 가 담당. 둘은 역할이 다르다 — Manifest 는 ingest 이력, Document 는 분류·소유 정보. spec 은 명시적으로 `knowledge.Document` 라고 지정.
- **대안 & 선택 이유**: (a) Document 신규 — 채택. spec/plan 그대로. 라벨 도메인이 knowledge(=무엇을 알고 있나) 에 속함. (b) `IngestManifest` 에 sensitivity 컬럼만 붙이기 — 거절. Manifest 는 `chat` 앱 소속, "이 파일은 무슨 등급?" 은 도메인이 다름. 또 같은 source_uri 가 새 hash 로 재인덱싱될 때 Manifest 가 SUPERSEDED 처리되므로 sensitivity 가 row 따라 유실/재기록되는 복잡성이 생긴다. (c) Document 와 IngestManifest 를 한 줄로 묶기 (FK) — 임무 범위 밖. Phase B 에서 ingest 파이프라인이 Document.get_or_create 를 호출하게 할 때 자연스레 처리.
- **결과**:
  - 변경 파일: `Rag_Chat/backend/knowledge/models.py`
  - 마이그레이션 생성: `knowledge/migrations/0002_document.py` (auto)

### chat.User.access_level
- **무엇을**: `Rag_Chat/backend/chat/models.py` 의 `User` 에 `access_level = CharField(choices=[(public/internal/confidential/restricted)], default="internal")` 추가.
- **왜**: spec §4.3 — Layer 2 retrieval 필터의 입력 변수. User 는 자기 access_level 이상 sensitivity 의 chunk 만 retrieve 한다. default=internal 인 이유는 부트캠프 사내 챗봇이 "사내 공유" 기본 권한을 가정하기 때문.
- **그때 상황**: `User` 모델은 이미 role(USER/MANAGER/ADMIN) 컬럼이 있었다. role 과 access_level 은 다른 차원 — role 은 Django Admin 권한, access_level 은 retrieval 필터. 두 차원을 합치자는 유혹이 있었지만, role 변경(=Admin 페이지 권한)과 sensitivity 라벨 변경은 운영 절차가 다르다 (HR 결재 vs 보안 결재) — 별도 컬럼이 정답.
- **대안 & 선택 이유**: (a) 별도 access_level 컬럼 — 채택. (b) role 에 confidential/restricted 단계 추가 — 거절. 의미가 섞임. (c) `knowledge.Sensitivity` 를 import 해서 choices 인자로 — 거절. import 순환 가능성. choices 리스트만 inline 으로 적었다 — 값은 같지만 의존성은 분리.
- **결과**:
  - 변경 파일: `Rag_Chat/backend/chat/models.py`
  - 마이그레이션 생성: `chat/migrations/0007_user_access_level_alter_ingestmanifest_id.py` (auto — ingestmanifest.id 의 BigAutoField alter 는 Django 4.2 DEFAULT_AUTO_FIELD 누적 noise 로, 데이터 손실 없음)

### ingest 파이프라인 — should_index 게이트 + chunk metadata sensitivity 복사
- **무엇을**: `Rag_Chat/backend/chat/ingest/pipeline.py:ingest_path()` 에 `sensitivity="internal"` 키워드 인자 추가. 함수 시작에서 `should_index(sensitivity)` 가 False 면 즉시 return 0 + log. loader/splitter 통과 후 각 raw_doc / chunk 의 `metadata.setdefault("sensitivity", sensitivity)` 로 라벨 복사.
- **왜**: spec §5.1 Layer 1 — restricted 문서는 벡터 스토어에 진입조차 못 한다. 그리고 §5.2 Layer 2 — chunk 의 메타데이터에 sensitivity 가 있어야 retrieval 필터가 작동. 두 동작을 한 함수 안에서 처리하는 게 데이터 흐름상 가장 결정적이고 디버깅 가능.
- **그때 상황**: `ingest_path` 는 manifest 체크 → loader → splitter → sink 의 4단 파이프. 기존엔 모든 chunk 가 sensitivity 메타 없이 흘러갔고, restricted 든 internal 이든 똑같이 Chroma 에 들어갔다. raw_docs / chunks 의 메타데이터에 `doc_sha256` 만 자동 부여하던 자리에 sensitivity 한 줄 더 끼워넣음.
- **대안 & 선택 이유**: (a) `ingest_path` 시그너처에 sensitivity 추가 — 채택. CLI/Upload/Celery 모두 같은 함수를 호출하므로 한 곳만 손대면 4 진입점이 다 커버됨. (b) sink (`ChromaSink.write`) 안에서 처리 — 거절. sink 는 "받은 chunk 를 저장" 이 책임. sensitivity 판단은 정책이라 pipeline 단계가 맞다. (c) loader 가 file path 에서 Document.objects.filter(source_uri=...).first().sensitivity 를 자동 lookup — Phase B 작업. Phase A 는 caller(=upload handler) 가 sensitivity 를 명시 전달하게 두는 게 단순.
- **결과**:
  - 변경 파일: `Rag_Chat/backend/chat/ingest/pipeline.py` (시그너처 + restricted 가드 + metadata setdefault 2곳)
  - 단위 검증: `should_index("restricted")` False, 그 외 True — `ShouldIndexTest` 2 ok

### RAGUtils.process_search_results / get_rag_context — ACL 필터 + redacted_count
- **무엇을**: `Rag_Chat/backend/chat/utils.py:RAGUtils.process_search_results(search_results, user_access_level="internal")` 시그너처 확장. 함수 내부에서 `apply_acl_filter(...)` 호출 → kept/redacted 분리 → 반환 dict 에 `redacted_count` 키 추가. `get_rag_context` 도 동일 인자를 forward.
- **왜**: spec §5.2 — retrieval response 가 redacted_count 를 노출해야 frontend 가 citation ribbon 에 `[수정됨·N건]` 배지를 그릴 수 있다. CLAUDE.md "무성 드롭 금지" 의 코드 표현.
- **그때 상황**: 기존 `process_search_results` 는 받은 docs 전부를 그대로 join 해서 context 문자열을 만들었다. ACL 개념이 없었고, frontend 가 결과 누락 사실을 알 길도 없었다. 호출처(`chat/views.py:43,45,517`, `chat/vector_metadata.py:295,327`, `chat/pipeline/modules.py:27`) 가 모두 user 객체에 접근 가능하므로 매개변수 추가는 점진적 마이그레이션이 가능 — 기본값을 internal 로 두어 기존 호출처는 한 줄 변경 없이 동작.
- **대안 & 선택 이유**: (a) `process_search_results` 시그너처 확장 + default — 채택. backward compatible. (b) 별도 `process_search_results_for_user(user)` 신규 함수 — 거절. 호출처가 5군데라 wrapper 만 늘어나고 결국 둘 다 유지해야 함. (c) RAGUtils 를 클래스 인스턴스로 바꿔 user 를 생성자 인자로 — 임무 범위 밖, 큰 리팩터. (d) views.py 의 `get_rag_context` wrapper 도 함께 user 인자 전달 — 미루는 게 안전. Phase A 는 "redacted_count 키가 반환된다" 까지가 exit criteria. caller 통합은 Phase D(UI) 와 함께.
- **결과**:
  - 변경 파일: `Rag_Chat/backend/chat/utils.py`
  - 검증: `GetRagContextRedactedCountTest.test_process_search_results_contains_redacted_count` ok — confidential chunk 가 internal user 에게서 redact 되어 context 에서 사라지고 redacted_count==1 반환.
  - 전체: `python manage.py test moderation -v 1` → Ran 12 tests in 0.002s OK
