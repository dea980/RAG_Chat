## 오늘 건드린 개념: "라벨 기반 접근통제 (label-based ACL)"

RAG 시스템에서 "이 chunk 를 이 사용자에게 보여줘도 되는가?" 를 결정하는 정책. 키워드 필터로는 못 막는 문제를 라벨 + 비교 한 줄로 해결한다.

<div class="analogy">
<strong>비유 — 회사 문서고 출입증.</strong><br>
회사 문서고에 들어가면 모든 캐비닛에 색 스티커가 붙어있다: <strong>흰색(공개) · 파랑(사내) · 노랑(대외비) · 빨강(기밀)</strong>. 직원은 자기 출입증에 적힌 색까지만 캐비닛을 열 수 있다.<br><br>
- 신입사원(출입증=파랑) 이 빨강 캐비닛 손잡이를 잡으려 하면? 잠겨있다. 그리고 보안실 로그에 "신입 OOO 가 빨강 캐비닛 시도" 가 찍힌다.<br>
- 신입이 검색대(=retrieval) 에 "M&A 자료" 라고 요청하면? 검색대는 "빨강 캐비닛 3건, 노랑 캐비닛 2건이 매칭됐지만 당신 권한 밖이라 5건 가렸음 — 결과 12건 중 표시 7건" 이라고 알려준다.<br>
&nbsp;&nbsp;→ 이 "가렸음 N건" 메시지가 바로 우리 시스템의 <code>redacted_count</code>.
</div>

## 왜 키워드 필터로는 못 막나

기존 코드(`moderation/filter.py`) 는 "이 단어가 텍스트에 있으면 차단" 식의 ForbiddenWord 매칭만 한다. 이건 출입증 검사가 아니라 **불심검문** 이다.

| 시나리오 | 키워드 필터 | 라벨 ACL |
|---|---|---|
| 신입이 작년 M&A 보고서 검색 | "M&A" 단어 차단 — but 보고서 본문에 "M&A" 가 안 적혀있고 "통합 거래" 라고만 적혀있으면 통과 | 보고서 자체가 confidential 라벨이라 신입(internal) 권한 부족으로 차단 |
| 차장이 자기 부서 코드네임 검색 | "Project Titan" 차단 — but 그건 차장이 알아도 되는 자기 프로젝트 | 차장(confidential) ≥ chunk(confidential) 이므로 통과 |
| 운영자가 신규 등급 추가 (예: top-secret) | 코드 수정 + 배포 필요 | DB 에 한 row 추가 (Phase B에서 admin UI 로 코드 변경 없이) |

<div class="tip">
<strong>핵심.</strong> 키워드 필터는 <strong>내용</strong> 을 본다 — 우회가 쉽고 false positive 가 많다. 라벨 ACL 은 <strong>출처</strong> 를 본다 — 출처가 분류되면 본문이 어떻게 적혔든 정책이 일관된다.
</div>

## 우리 구현의 핵심 한 줄

```python
# moderation/levels.py
SENSITIVITY_LEVEL = {"public": 0, "internal": 1, "confidential": 2, "restricted": 3}

def can_access(user_level: str, content_level: str) -> bool:
    return SENSITIVITY_LEVEL[user_level] >= SENSITIVITY_LEVEL[content_level]
```

`>=` 한 줄. 이게 가능한 이유는 sensitivity 가 **단조 ladder (monotone ladder)** 라서다 — 빨강 출입증은 노랑/파랑/흰색 캐비닛까지 다 열린다. 모든 차원이 이렇게 깔끔하지 않다는 게 함정인데(부서 RBAC, 시간 제한 등), 부트캠프 범위에서는 단일 ladder 만으로 충분.

<div class="warn">
<strong>주의 — 라벨이 메타데이터에 없으면?</strong><br>
옛 청크는 sensitivity 메타가 없을 수 있다. 코드는 <code>DEFAULT_LEVEL = "internal"</code> 로 안전측 fallback. "기록 없는 데이터는 사내 정도로 본다" 는 정책 — public 으로 fallback 하면 옛 chunk 가 외부 유출 가능성이 생긴다.
</div>

## 4 boundary 가 같은 ladder 를 공유하는 이유

`moderation/levels.py` 는 ORM 의존이 0이다. 이게 의도된 설계:
1. **업로드** 경계: 운영자가 Document.sensitivity 부여 → `should_index()` 로 restricted 차단.
2. **질문** 경계: 사용자 입력 검사 (Phase C — PII 매칭, Phase A 범위 밖).
3. **검색결과** 경계: chunk 메타데이터의 sensitivity 와 User.access_level 비교 → `apply_acl_filter()`.
4. **답변** 경계: LLM 응답 검사 (Phase C 범위).

네 경계가 모두 `from moderation.levels import ...` 한 줄로 같은 ladder 를 import 하므로, 운영자가 새 등급을 추가하면 4 boundary 가 동시에 갱신된다.

<div class="analogy">
<strong>비유 — 회사 전체가 같은 색표를 쓰기.</strong><br>
출입증 색표가 정문 보안, 문서고, 메일 시스템, 회의실 예약 시스템마다 달랐다면? 신입이 "파랑인 줄 알았는데 회의실에서는 노랑이라며 거절당함" 같은 혼란이 생긴다. 회사 전체가 같은 4색표(public/internal/confidential/restricted) 를 공유하는 게 ladder 공유의 본질.
</div>

## 무성 드롭 (silent drop) 금지 — `redacted_count` 의 의의

retrieval 에서 chunk 가 가려졌는데 사용자가 모르면? 답변이 "정보가 없습니다" 처럼 보여 사용자가 가짜 답을 신뢰하거나, 거꾸로 "왜 결과가 없지" 라며 다시 비슷한 질문을 반복한다. 둘 다 신뢰 비용.

우리 응답은:
```python
{
  "context": "...",          # 권한 통과한 chunk 들의 본문
  "docs": [...],             # 권한 통과한 chunk 객체
  "image_paths": [...],
  "redacted_count": 3        # ← 가려진 갯수 노출
}
```

Frontend (Phase D) 는 이 숫자로 citation ribbon 끝에 `[수정됨·3건]` amber 배지를 그린다. 사용자가 "내가 권한 부족이구나" 를 알면 결재 요청으로 자연스레 흐른다.

<div class="tip">
<strong>핵심.</strong> 보안 정책은 차단만이 아니라 <strong>차단 사실의 가시화</strong> 까지 포함해야 신뢰가 유지된다. CLAUDE.md "무성 드롭 금지" 가 코드로 박힌 자리가 바로 <code>redacted_count</code>.
</div>

## TDD 가 이번에 잡아준 함정

테스트 먼저 쓰면서 자연스레 결정한 케이스 3개:

1. **`can_access("god", "public")` — 오타 권한값은 KeyError**: silent False 면 권한 오타가 "그냥 안 보임" 으로 묻힌다. KeyError 로 시끄럽게 죽는 게 운영 사고에 안전.
2. **sensitivity 메타가 없는 chunk — default internal**: 옛 데이터 호환. 위 warn 박스 참고.
3. **권한 초과 chunk 의 page_content 가 context 문자열에 들어가지 않음**: `process_search_results` 가 join 전에 필터링해야 — 한 줄 잘못 쓰면 본문 노출. 테스트가 이 순서를 명시 검증.

만약 코드 먼저 쓰고 테스트 뒤에 썼다면, "redacted_count 키 존재" 같은 통과형 테스트만 추가하고 위 3개 케이스는 놓쳤을 가능성이 크다.
