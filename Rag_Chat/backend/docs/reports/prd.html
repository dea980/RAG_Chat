Triple Chat — 사내 RAG 챗봇 PRD

영업팀 등 비엔지니어 부서가 제품/담당자 정보를 자연어로 찾고, 관리자가 검수·감사할 수 있는 사내 챗봇.

Status: MVP 구현 완료
Stage: 배포 직전 · 영업팀 베타
Branch: main

1 · 시스템 개요 overview

Problem 영업팀·고객지원팀이 제품 사양·가격·담당자 정보를 매번 PDF/엑셀/슬랙에서 수동으로 찾는 데 시간을 과도하게 소비. 정보 분산 → 잘못된 응답을 고객에게 전달하는 사고 위험.
Users USER 영업·CS 직원 (자연어 질문) · MANAGER 부서장 (팀원 활동 리포트) · ADMIN C-Level/IT (금지어·RAG 문서·감사 관리)
Goal 1. 영업팀 질문 평균 응답 3~5초.
2. 매 응답에 대해 (질문→컨텍스트→답변)을 감사 가능.
3. 대외비/PII가 외부 LLM으로 평문 송신되지 않도록 다층 방어.
4. 관리자가 Django Admin에서 금지어를 직접 운영/검수.
Non-goal 소비자 대상 챗봇·다국어·HA 멀티노드·완전 자체 호스팅 LLM (단계적, 부록 A 참조).
Stack Streamlit · Django REST · Celery · Redis · PostgreSQL 16 · FAISS/Chroma · LangChain · Gemini(기본)/Qwen(실험) · Docker Compose · GitHub Actions

1.1 시스템 다이어그램

┌────────────────────────────────────────────┐ │ 사용자 (영업/CS) │ └────────────────────────────────────────────┘ │ 자연어 질문 ▼ ┌──────────────────────┐ │ Streamlit (8501) │ └──────────────────────┘ │ ▼ ┌────────────────────────────────────────────┐ │ Django REST (8000) │ │ ┌──────────────────────────────────────┐ │ │ │ AuditLogMiddleware (모든 호출 기록) │ │ │ └──────────────────────────────────────┘ │ │ │ │ │ ┌──────────────┼─────────────────┐ │ │ ▼ ▼ ▼ │ │ chat knowledge moderation │ │ (RAG) (deterministic (BLOCK/MASK/ │ │ search API) WARN) │ │ │ │ │ │ │ ▼ ▼ ▼ │ │ FAISS Postgres tables ForbiddenWord │ │ Chroma ModerationLog│ │ │ │ │ ▼ (INBOUND filter → LLM → OUTBOUND filter) │ Gemini / Qwen API ◀── 향후: Ollama/vLLM │ └────────────────────────────────────────────┘ │ ▼ PostgreSQL + Redis + AuditLog

1.2 KPI

  • 응답 시간: p50 ≤ 3s, p95 ≤ 5s
  • 검색 정확도: recall@5 ≥ 0.80 (12문항 영업팀 평가셋 기준)
  • 금지어 누락률: ModerationLog 미반영 응답 0건 / 주
  • 감사 커버리지: 모든 mutating API 호출의 100%가 AuditLog에 기록

2 · Part 1 · chat — RAG 파이프라인 app: chat

Problem제품 자료가 분산되어 영업이 자연어로 답을 빨리 못 얻음.
UsersUSER 모든 임직원
Goal질문 → 벡터검색 → reasoning → generation → 응답 + 모든 단계 추적 가능
Non-goal스트리밍 응답(추후), 멀티턴 기억(현재 Redis 단순 히스토리), 다국어

2.1 Requirements

  • POST /api/v1/triple/chat/ · 입력 {user_id, question} → 출력 {response, chat_id, images}
  • 모든 응답은 Chat, SearchLog, RagData에 추적 가능 row를 남김
  • 벡터스토어는 chunk_size=1000, chunk_overlap=200 기본 (부록 B에서 추후 150 권장)
  • provider 추상화로 Gemini ↔ Qwen 환경변수 전환
  • 금지어 필터가 LLM 호출 전·후 모두 적용

2.2 Solution / 핵심 코드

  • 모델: chat.Chat, chat.SearchLog, chat.RagData, chat.User(Role 추가)
  • 파이프라인: chat/pipeline/modules.py — Retrieve → Reasoning → Generation (LangChain)
  • 세션 정합성: refresh_user_session() — Redis TTL ↔ DB expired_datetime 단일 윈도우
  • 헬스체크: /api/v1/triple/health/, /health/ready/

2.3 Metrics

  • SearchLog row가 Chat row 수와 ≥ 95% 일치 (검증된 trace 비율)
  • Provider별 평균 응답 시간 메트릭 (Stage 2)

2.4 Risks

  • chunk 정책이 데이터 갱신 후 노후화 → 부록 B의 A/B harness를 정기 실행 (CI 1회/주)
  • Gemini API 장애 시 fallback 없음 → 향후 provider fallback chain

3 · Part 2 · knowledge — 지식베이스 app: knowledge

Problem“이 제품 담당이 누구야”·“어느 부서가 이 솔루션 다뤄?” 문의가 매일 반복. LLM이 부정확하게 답하는 영역이라 결정적 조회가 더 안전.
UsersUSER 영업/CS 직원 (조회) · MANAGER 부서장 (편집) · ADMIN IT (CRUD)
GoalLLM 우회 검색 API + Django Admin에서 CRUD
Non-goal외부 ERP 연동 (Stage 2), 권한 세분화

3.1 Requirements

  • 모델: Department (계층 가능), Contact (담당자), Product (제품/서비스/솔루션, JSON specs)
  • 검색 API 3개:
    • GET /api/v1/knowledge/products/?q=&category=
    • GET /api/v1/knowledge/contacts/?q=&department=
    • GET /api/v1/knowledge/departments/
  • 응답 ≤ 50건 페이지(현재 단순 slice, 향후 cursor)
  • Django Admin에 등록 — autocomplete + search

3.2 Solution

  • 파일: backend/knowledge/{models,admin,views,urls}.py
  • Product 검색은 name__icontains, description__icontains OR
  • 응답 JSON에 primary_contact를 inline 포함 → 한 번의 호출로 “제품 + 담당자”까지

3.3 Metrics

  • 검색 API p95 ≤ 300ms (DB 인덱스 + 50건 cap)
  • 영업팀의 “담당자 누구야” 챗봇 질문 비율 → 1주 후 감소 확인

3.4 Risks

  • Department 계층(parent self-FK) 깊어질 때 자식 조회 N+1 — Stage 2에서 prefetch
  • specs JSONField 스키마 비통일 → 부서별 템플릿화는 Phase 2

4 · Part 3 · moderation — 금지어 검수 app: moderation

Problem대외비/PII/경쟁사 언급이 그대로 외부 LLM으로 송신되는 위험. 관리자가 단어를 정책으로 운영·검수할 수 있어야 함.
UsersADMIN (정책 설정·검수) · 시스템 내부 (필터 적용)
GoalBLOCK / MASK / WARN 다단계 정책을 INBOUND·OUTBOUND 양방향에 적용, 모든 탐지를 검수 가능한 로그로 남김
Non-goal정규식 룰(현재 substring), 다국어 형태소 분석, ML 기반 탐지

4.1 Requirements

  • 모델
    • ForbiddenWord: word, category, severity ∈ {MASK, WARNING, BLOCK}, direction ∈ {INBOUND, OUTBOUND, BOTH}, mask_replacement
    • ModerationLog: action ∈ {BLOCKED, WARNED, MASKED}, source ∈ {INBOUND, OUTBOUND}, original/sanitized excerpt, reviewed 플래그
  • 정책
    • BLOCK: LLM 호출 0회. 403 응답. 사용자에겐 차단 메시지만.
    • MASK: [REDACTED] 등으로 치환 후 LLM에 전달, ModerationLog.MASKED 기록.
    • WARNING: 통과시키되 ModerationLog.WARNED 기록.
  • 검수 페이지: Django Admin /admin/moderation/
    • ForbiddenWord 인라인 편집 (severity/direction/is_active)
    • ModerationLog에 reviewed 체크박스 + reviewer_note

4.2 Pipeline 연결 위치

question │ ▼ [Chat 저장] │ ▼ [INBOUND moderate] ───► BLOCK → 403 + ModerationLog │ (sanitized) ▼ RAG retrieve → reasoning → generation │ ▼ [OUTBOUND moderate] ───► BLOCK → "응답 표시 불가" │ (sanitized) ▼ Chat.response_text 저장 + 응답

4.3 Solution / 핵심 코드

  • backend/moderation/filter.py · apply(text, source, user, chat) → ModerationResult
  • BLOCK은 BlockedByModerationError 예외로 short-circuit
  • 치환은 right-to-left index walk로 한 패스 처리
  • chat.views.ChatAPIView에서 inbound/outbound 모두 호출

4.4 Metrics

  • 주간 ModerationLog 건수 · 액션별 비율 · 미검수 잔여 건수
  • BLOCK 발동률 (분모: 총 chat 호출) — 정책 강도 모니터링

4.5 Risks

  • substring 매칭의 false positive (예: 단어 일부) — 단어 경계 정규식으로 강화 예정
  • OUTBOUND BLOCK 시 사용자 경험 (응답 차단) — Stage 2에 대체 응답 템플릿 분기

5 · Part 4 · audit — 감사 로그 app: audit

Problem누가 무엇을 호출했고 응답 코드가 무엇이었는지 추적 불가. 보안 사고 발생 시 incident replay 불가능.
UsersADMIN 보안/감사 담당
Goal모든 mutating API 호출의 100%를 비차단(non-blocking) 미들웨어로 기록
Non-goal요청 본문 자체 저장 (PII 누출 위험), 외부 SIEM 송출 (Stage 3)

5.1 Requirements

  • 모델 AuditLog: user, action, resource, resource_id, method, path, status_code, detail(JSON), ip_address, user_agent, created_at
  • 인덱스: created_at desc, (action, created_at desc)
  • 미들웨어가 request 종료 후 1 row insert; insert 실패해도 응답에 영향 없음
  • healthcheck / static / 관리자 i18n 경로는 제외 (잡음 차단)
  • Django Admin은 read-only (변조 방지)

5.2 Solution

  • backend/audit/middleware.py · AuditLogMiddleware
  • backend/audit/admin.py · has_add_permission=False, has_change_permission=False
  • user 식별: 현재는 request.data.user_id 기반 (JWT 전환 시 토큰 subject로 교체)

5.3 Metrics

  • 커버리지: chat 호출 수 ≈ AuditLog (http.post) 수 (drift ≤ 1%)
  • 저장 latency 95th ≤ 30ms — 미들웨어가 응답 latency를 가리지 않도록

5.4 Risks

  • 장기 보관 시 row 폭증 → Stage 2에서 30일 retention + cold storage
  • 익명 사용자 호출(미들웨어가 user=None) — Phase 1 JWT 적용 후 정리

6 · 부록 A · 보안 / 대외비 대응 cross-cutting

위협외부 LLM 데이터 송출 · 무인증 API · 평문 로그 · 하드코딩 SECRET_KEY · CORS 부재
이번 단계 처치 1) DEBUG=0 + 기본 SECRET_KEY 부팅 거부
2) CORS allowlist env-driven (CORS_ALLOWED_ORIGINS)
3) INBOUND/OUTBOUND 금지어 필터 + MASK
4) 모든 API 호출 AuditLog 기록
5) 헬스체크 endpoint (incident detection)
잔여 위험JWT 미적용, HTTPS 미강제, Redis AUTH, DB 컬럼 암호화, 외부 LLM 의존
로컬 LLM 경로provider 추상화 활용 — Ollama PoC(Stage 2) → vLLM(Stage 3). 자세한 절차는 backend/docs/security.md §4

6.1 운영자 매뉴얼 (요약)

  1. Django Admin 슈퍼유저 생성 → /admin/ 로그인
  2. Moderation › Forbidden words에 시드 입력:
    • MASK: 고객명, 사번 패턴 (예: 010-XXXX-XXXX)
    • WARNING: 경쟁사명
    • BLOCK: 미공개 코드네임, M&A 키워드
  3. Moderation › Moderation logs를 매일 검수 → reviewed=True
  4. 대외비 등급 상향 시 — security.md §4의 Ollama 절차 따라 LLM 사내 전환

7 · 부록 B · 검증 (chunk A/B + CI) quality

7.1 Chunk Size A/B Harness

  • 평가셋: 영업팀 시나리오 12문항 (backend/chat/tests/evals/dataset.jsonl)
  • retriever: BM25 (Gemini API 의존 없음 — CI에서도 돌릴 수 있음)
  • 지표: recall@k — expected_keywords 중 top-k chunk에 등장한 비율
chunk_sizerecall@5
800.569 (overlap=0) → 0.653 (overlap=30)
1500.833 ← sweet spot
250 이상0.789 (한 행이 한 chunk)

결론: production의 chunk_size=1000은 안전하나, 본 데이터셋에선 150이 +4.4%p 개선. 운영 적용 전 controlled rollout 필요.

7.2 GitHub Actions CI

  • lint: flake8 (pragmatic ruleset)
  • django-tests: Postgres + Redis 서비스 컨테이너, pytest
  • retrieval-eval: chunk A/B harness, 결과를 워크플로 artifact + Job Summary로 노출
  • docker-build: backend / frontend 이미지 빌드 검증

8 · 로드맵 / 리스크 future

Stage 1 (현재) Streamlit + Django, RBAC 데이터모델, 금지어 검수 Admin, 감사 로그, Postgres, GitHub Actions, 외부 LLM(Gemini) — 영업팀 베타 가능 수준.
Stage 2 (1~2개월) JWT endpoint protection, 응답 스트리밍(SSE), 사내 Ollama PoC, ModerationLog retention 정책, knowledge specs 템플릿화.
Stage 3 (분기) vLLM 사내 전환 (외부 LLM fallback only), 멀티노드/HA, AuditLog SIEM 송출, knowledge ERP 연동.

8.1 Open risks

  • 외부 LLM 의존 — Stage 2/3 전까지 정책적으로 “고급 대외비는 챗봇에 입력 금지” 사용자 가이드 필요
  • 금지어 substring 매칭의 false positive — 단어 경계 정규식 강화
  • knowledge 데이터 시드의 정확성은 운영 단계 의존 — 부서별 owner를 명확히 지정
