1. 출발점 — 무엇이 문제였나

프로젝트 처음 진단 결과 ingest layer 자체가 없었다:

  • CSV/XLSX 만 처리하는 if/else 가 chat/build_vector_store.py + chat/management/commands/build_vectors.py 두 군데에 흩어짐
  • 같은 파일 두 번 빌드 시 Chroma 에 중복 적재 — 7행 CSV 가 88 청크 누적된 hidden bug
  • 포맷 추가하려면 빌더 코드를 수정해야 함 (확장성 0)
  • chat_ragdata 는 query 시점에만 채워지므로 query 안 돌면 0건 — 이건 진단 정정한 부분 (ingestion 문제 아님)
  • HWP / PDF / OCR 같은 한국 기업 문서 포맷 처리 경로 부재

강의 7강의 "인제스천 4분류" 프레임이 이 빈 자리의 가이드 — 텍스트 추출형 / OCR 필요형 / 구조화 데이터 / 전용 포맷.

2. Phase 1 — Skeleton

플러그인 등록제 + 표준 인터페이스

완료

해결한 문제

포맷 추가가 빌더 if/else 분기 추가가 되는 구조 → loader 파일 하나 + 데코레이터 한 줄로 끝나는 구조로 갈음.

핵심 인터페이스 (chat/ingest/base.py)

@dataclass
class RawDoc:
    content: str
    source_file: str
    source_type: str        # "csv" | "pdf" | "hwp" | ...
    page: int | None = None
    section: str | None = None
    metadata: dict = field(default_factory=dict)

class BaseLoader(Protocol):
    extensions: tuple[str, ...]
    source_type: str
    def load(self, path: str) -> Iterable[RawDoc]: ...

class BaseSplitter(Protocol):
    def split(self, doc: RawDoc) -> Iterable[RawDoc]: ...

class BaseSink(Protocol):
    def write(self, docs) -> WriteResult: ...
    def delete_ids(self, ids: list[str]) -> int: ...

추가된 파일

+ chat/ingest/__init__.py + chat/ingest/base.py # Protocol 정의 + chat/ingest/registry.py # @register + chat/ingest/pipeline.py # 오케스트레이션 + chat/ingest/loaders/structured/{csv,excel}.py + chat/ingest/splitters/{recursive,row}.py + chat/ingest/sinks/chroma.py ~ chat/management/commands/build_vectors.py # 70+줄 → 35줄, pipeline 호출만

학습 포인트

  • Protocol vs ABC — duck typing 인터페이스. loader 가 명시적 상속 없이 통과
  • side-effect import — loaders/__init__.py 가 하위 모듈 import 만 해도 @register 가 실행되어 registry 채움. Django app 등록과 같은 패턴
  • 3 Protocol 만으로 RAG 인제스천 파이프라인 전체가 표현됨

3. Phase 2 — Manifest (멱등성)

SHA256 기반 dedup + 결정론적 청크 id

완료

해결한 문제

  • 같은 파일 두 번 빌드 시 Chroma 중복 적재 (이전의 88청크 누적)
  • 파일 내용 바뀌어도 옛 청크가 자동 제거되지 않음 (stale 누적)
  • 실패 추적 불가 — 재시도 여부 판단 못 함

핵심 구조

IngestManifest 모델
  source_uri    : 'file:///abs/path' 또는 'upload://name'
  doc_sha256    : 파일 hex digest
  loader        : 'csv' | 'pdf' | ...
  splitter      : 'row' | 'recursive' | ...
  chunk_count   : 7
  chroma_ids    : ["abc...", ...]   # 삭제용
  status        : OK | FAILED | SUPERSEDED
  unique_together = (source_uri, doc_sha256)
ChromaSink._chunk_id(chunk) = sha256(
  chunk.source_file + chunk.section +
  str(chunk.metadata["chunk_index"]) +
  chunk.content
)
→ 같은 청크 = 같은 id = Chroma 가 upsert

Pipeline 동작

  1. loader 결정 + SHA256 계산
  2. already_ingested(uri, sha) → OK 면 skip
  3. previous_versions(uri, exclude=sha) → 옛 chroma_ids 삭제 + SUPERSEDED 표시
  4. 실제 적재 → record_success / record_failure

검증

1st (fresh)        chunks=7  manifest=1
2nd (same hash)    chunks=0  manifest=1   ← skip
3rd (force=True)   chunks=7  manifest=1   ← update_or_create
unknown ext        ValueError ✓
file_sha256 stable ✓

학습 포인트

  • 멱등성이 운영 안정성의 토대 — 비동기·캐싱 같은 무거운 도구 도입 전에 동기 ingest 가 idempotent 해야 함
  • update_or_create — unique 제약과 friction 없이 force 재실행 처리
  • 결정론적 id 의 가치 — Chroma 의 add 가 upsert 처럼 동작. 외부 시스템과의 정합성 자동

상세: ingest_phase2_manifest.md

6. Phase 3 Integration — Dispatch + Upload Manifest

Splitter 자동 dispatch + Upload 의 manifest 통합

완료

해결한 두 이슈

Phase 3 loader 가 들어오면서 드러난 dispatch / manifest 우회 문제를 한 PR 로 통합.

적용된 변경

~ chat/ingest/splitters/__init__.py # default_splitter_for + splitter_by_name 신설 ~ chat/ingest/pipeline.py # splitter/sink optional + source_uri_override ~ chat/management/commands/build_vectors.py # RowSplitter 하드코딩 제거 ~ chat/ingest_views.py # Upload → pipeline.ingest_path 경유

def default_splitter_for(source_type): ...

# pipeline.py
def ingest_path(path, splitter=None, sink=None, *,

    ...

Upload API 변경

# 이전: ChromaSink().write(chunks)  ← manifest 우회
# 이후:
def _ingest_uploaded_file(tmp_path, *, original_name):
    return ingest_path(
        tmp_path,
        source_uri_override=f"upload://{original_name}"
    )
# 효과: Phase 2 manifest 가 그대로 적용 → 중복 업로드 자동 skip

검증 (8개 시나리오)

1. default_splitter_for         OK (csv→row, pdf/txt→recursive)
2. splitter_by_name             OK
3. CSV via pipeline             chunks=7 splitter=row     ← 자동
4. TXT with override            chunks=3 splitter=recursive
   source_uri='upload://mydoc.txt'
5. Same upload re-attempt       chunks=0                  ← manifest skip
6. Content changed              chunks=4, SUPERSEDED=1    ← 옛 버전 정리
7. build_vectors path (csv)     chunks=7 splitter=row

학습 포인트

  • Dispatch 한 곳에 모이기 — source_type → splitter 매핑이 한 dict. Phase 4 splitter 추가가 한 줄로 끝남
  • 안정 키 (upload://name) — 임시 파일 경로의 변동성을 의미적 식별자로 추상화
  • Optional 인자 + default — ingest_path(path) 만으로 충분, 명시 필요 시만 인자
  • CLI / API / 향후 Celery 가 같은 함수 한 곳을 경유 → 자동 일관성
