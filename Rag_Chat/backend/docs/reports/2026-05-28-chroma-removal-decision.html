2. 선택지 3가지

A) Chroma 유지 (현 상태 — 폴백으로 남겨둠)

장점단점
  • pgvector 장애 시 Chroma로 자동 폴백
  • 코드 변경 없음 — 리스크 제로
  • 비교 테스트 가능 (결과 검증용)
  • chromadb 패키지 계속 설치 (용량 + 취약점 관리)
  • vector_store/ 디렉토리 20MB 유지
  • LangChain deprecated 경고 로그에 계속 노출
  • 두 저장소 동기화 안 됨 — 새 ingest는 pgvector만 갈 수 있음

적합 시점: pgvector 안정성이 검증되기 전 1~2주 과도기

B) Chroma 제거 — pgvector 단독

장점단점
  • 인프라 단일화 — PostgreSQL 하나로 관리
  • chromadb 의존성 제거 (설치 시간 ↓, 보안 표면 ↓)
  • deprecated 경고 해소
  • 코드 단순화 — 폴백 분기 삭제
  • ACL이 SQL 레벨에서 끝 — 성능·정확도 ↑
  • PostgreSQL 다운 시 검색 불가 (하지만 Django 자체도 죽음)
  • 롤백하려면 Chroma 재설치 + 데이터 복원 필요
  • 코드 변경 필요 (아래 목록 참고)

적합 시점: pgvector 검색 결과가 Chroma와 동등함을 확인한 후

C) Chroma → langchain-chroma 업그레이드 (deprecated 해소만)

장점단점
  • deprecated 경고 해소
  • 코드 변경 최소 (import 경로만)
  • 여전히 2개 벡터 DB 운영
  • ACL은 여전히 Python 후처리
  • pgvector와 이중 관리 — 의미 없는 복잡도

적합 시점: pgvector 전환을 안 했을 때만 의미 있음. 지금은 불필요

4. 리스크 분석

Q: PostgreSQL 죽으면?
A: Django 자체가 PostgreSQL 의존 → PG 죽으면 Chroma 있어도 서비스 불가. Chroma 폴백이 실질적 안전망이 아님.
Q: 검색 품질 차이?
A: 동일한 임베딩(3072차원 Gemini) + 동일한 코사인 거리 계산. 수학적으로 동일한 결과. 단, 부동소수점 정밀도 차이로 순위가 미세하게 다를 수 있음 — 실사용에 영향 없음.
Q: 롤백이 필요하면?
A: vector_store/ 백업 보관 + chromadb 재설치하면 복원 가능. Git에서 삭제된 코드도 복구 가능.
