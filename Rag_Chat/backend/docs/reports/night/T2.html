배경 (전체 임무 한 줄)

Phase 3/4 에서 HeadingSplitter(markdown 헤딩 계층), ClauseSplitter(제N조 / Article N 조항 단위) 두 splitter 가 backend 에 추가됐는데 frontend chunk_lab 페이지의 선택 UI 가 옛 2종(recursive, row)만 노출 중이라 사용자가 신규 splitter 를 실험할 길이 없는 상태였다. T2 의 미션은 "이 노출 갭만 메우는 frontend 1줄 패치 + 검증".

아래는 missions.md §T2 의 5개 임무 항목을 순서대로 처리한 기록. 각 항목마다 같은 5줄 포맷(무엇 / 왜 / 그때 상황 / 대안 & 선택 이유 / 결과)으로 결정 추적을 남긴다.

1. splitter selectbox 옵션 리스트 현황 확인

  • 무엇을: Rag_Chat/frontend/pages/chunk_lab.py 를 끝까지 읽고 st.selectbox("전략", ...) 호출 위치(214행)에서 현재 옵션이 ["recursive", "row"] 임을 확정. help 문구·페이지 하단 expander 의 splitter 설명도 같은 상태인지 함께 확인.
  • 왜: 패치 전에 "지금 frontend 가 사용자에게 무엇을 노출하고 있는가" 를 단정해야 변경 범위(=옵션 리스트 한 줄 + 그에 딸린 도움말 두 군데)가 확정된다. 추측으로 한 줄만 고치면 expander 설명이 옛 2종만 안내해 UI/문서 불일치가 남는다.
  • 그때 상황: chunk_lab.py 학습용 메모에 "추후 조항 단위 splitter 가 더 좋다" 는 미래형 문장이 그대로 박혀 있었다 — 즉 "도입 예정" 단계에서 멈춰 있고 실제 도입(backend) 은 진작 끝났는데 frontend 가 텍스트만 옛날 상태였다.
  • 대안 & 선택 이유: 대안 없음. 변경 전 현황 파악은 모든 임무의 기본 단계.
  • 결과: 변경 대상 3 군데 위치 확정 — (a) selectbox options(214–218행), (b) selectbox help(218행 내), (c) bottom expander markdown(322–325행).

2. selectbox 옵션을 4종으로 확장

  • 무엇을: ["recursive", "row"] → ["recursive", "row", "heading", "clause"] 로 한 줄 교체. help 문구를 "recursive = 길이 기반 / row = 1행 1청크 / heading = markdown heading 계층 / clause = 제N조·Article N 조항 단위" 로 4줄 설명으로 확장.
  • 왜: 사용자가 chunk lab 에서 신규 splitter 를 클릭 한 번으로 실험할 수 있어야 하고, 도움말이 옛 2종만 설명하면 신규 옵션 선택 시 "이게 뭐 하는 건지" 알 수 없다.
  • 그때 상황: backend _BY_NAME 에 4종이 이미 등록돼 있었지만 frontend 의 옵션이 두 개라 backend 능력의 절반만 노출 중. backend 변경은 임무 영역 밖이라 손대지 않음.
  • 대안 & 선택 이유: (a) selectbox 정적 리스트 — 채택, 1줄 변경으로 충분. (b) backend 가 splitter 이름 목록을 돌려주는 메타 API (/splitter-names/) 신설 후 frontend 가 동적으로 fetch — overkill. _BY_NAME 갱신이 자주 일어나지 않고, 신설은 yagni. (c) splitter 별 sub-form (예: clause 의 regex pattern 입력) 노출 — 임무 범위 밖, splitter 들이 인자 없이 동작하도록 이미 디자인됨.
  • 결과: Rag_Chat/frontend/pages/chunk_lab.py:216 한 줄 + help 문구 확장. grep 결과: 216: ["recursive", "row", "heading", "clause"], — 의도된 한 곳에서만 매칭.

3. backend 호출 시 splitter 파라미터 전달 경로 확인 (dry-run)

  • 무엇을: call_preview 함수(chunk_lab.py:39–60)가 data["splitter"] = splitter 로 form-data 에 그대로 실어 POST 하는지 확인. backend 쪽은 chat/ingest_views.py 의 preview view 가 splitter_by_name(name, chunk_size=..., chunk_overlap=...) 로 받아 dispatch — 그 경로가 살아있는지 grep 으로 trace.
  • 왜: 옵션을 노출만 하고 backend 가 "heading" 이라는 문자열을 못 받거나 무시하면 UI 만 거짓말. 실제로 신규 옵션 선택 → splitter dispatch → 결과 JSON 까지 단절 없이 흐르는지 코드 경로를 끝까지 따라가야 한다.
  • 그때 상황: chat/ingest_views.py:25 에 from .ingest.splitters import splitter_by_name, :33 에 return splitter_by_name(name, chunk_size=chunk_size, chunk_overlap=chunk_overlap) — preview API 가 splitter 이름을 dict lookup 으로 정확히 해석 중. URL 매핑(chat/urls.py:20)도 /ingest/preview/ 로 살아있어 frontend 의 PREVIEW_URL 과 매치.
  • 대안 & 선택 이유: 대안 없음 — 단순 검증 단계. 실제 HTTP 호출까지 안 가도 코드 경로가 끊김 없이 이어진 게 확인되면 충분(임무 정의도 "그대로 전달되는지 확인" 까지).
  • 결과: dispatch 경로 무결성 확정. backend 변경 불필요.

4. 새 옵션 선택 시 정상 응답 시뮬 (backend splitter 매핑 파일 확인)

  • 무엇을: Rag_Chat/backend/chat/ingest/splitters/__init__.py 의 _BY_NAME dict 가 {"recursive", "row", "heading", "clause"} 4 키를 정확히 갖고 있는지, 각 splitter 클래스가 import 되는지 확인. 동시에 DEFAULT_BY_SOURCE 가 heading/clause 를 의도적으로 제외했다는 주석(29–31행) 확인.
  • 왜: frontend 가 splitter="heading" 으로 보냈을 때 backend 가 RecursiveSplitter 로 fallback 해버리면 사용자는 "heading 선택했는데 결과가 recursive 와 똑같다" 는 침묵 버그를 만난다. dict 키 4개 확인이 곧 "신규 옵션 클릭 시 진짜 신규 splitter 가 도는지" 의 보장.
  • 그때 상황: heading/clause 가 DEFAULT_BY_SOURCE(확장자 자동선택) 에서 빠진 이유까지 코드 주석에 명시 — 자동 선택은 청킹을 망칠 수 있어 opt-in 만 허용. 즉 chunk_lab 의 selectbox 가 곧 그 opt-in 통로 본체. backend 디자인이 이미 "사용자가 명시 선택해야 함" 을 전제로 짜여 있었다.
  • 대안 & 선택 이유: (a) splitter dispatch 동작을 실제 HTTP 호출까지 가서 검증 — django 기동 필요해 야간 단독 검증 비용↑. dict 확인으로 충분. (b) backend 단위 테스트(tests/ingest/test_splitter_dispatch.py) 를 새로 돌려 검증 — 이미 존재하고 검사 항목이 동일. 추가 실행 안 함.
  • 결과: _BY_NAME 4 키 확정. _BY_NAME.get(name, RecursiveSplitter) 의 fallback 동작도 확인(오타 시 침묵 fallback) — 학습 노트의 연습문제 2번에 이 fallback 함정을 기록.

5. Streamlit 페이지 import / 구문 검증

  • 무엇을: python3 -c "import ast; ast.parse(open('Rag_Chat/frontend/pages/chunk_lab.py').read())" 으로 구문 유효성 확인. 미션 정의가 "streamlit run 까지는 안 해도 됨 — ast.parse 통과면 OK" 였음.
  • 왜: streamlit 페이지가 import 단계에서 SyntaxError 면 사용자가 페이지를 열자마자 에러 화면을 본다. ast.parse 는 import / 실행 없이 구문만 검증하는 가장 가벼운 단계라 야간 단독 검증에 적합.
  • 그때 상황: 첫 호출 시 python 명령어가 없어 fail(command not found: python). macOS 환경의 Python 은 python3 로만 노출돼 있어 명령어 교체 필요.
  • 대안 & 선택 이유: (a) python3 -c "import ast; ast.parse(...)" — 채택, 가벼움. (b) streamlit run frontend/pages/chunk_lab.py 실제 기동 — backend 도 같이 띄워야 의미 있는 검증이 되는데 야간 단독 실행은 부적합. (c) python3 -m py_compile chunk_lab.py — 동일 효과지만 .pyc 생성 부작용 있음.
  • 결과: ast ok 출력. 구문 OK 확인. 실제 streamlit/django 기동 검증은 사용자가 깬 뒤 통합 단계에서 진행.
