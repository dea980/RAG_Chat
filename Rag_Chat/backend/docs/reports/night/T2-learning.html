오늘 건드린 개념: "Splitter"

RAG 파이프라인의 두 번째 단계인 청킹(chunking) 을 담당하는 모듈. 원문서를 어떤 단위로 자르냐가 검색 품질을 좌우한다.

비유 — 김밥집 절단대.
김밥을 통째로 손님 접시에 올리면 한 입에 들어가지 않는다. 그렇다고 1mm 단위로 다지면 김밥인지 죽인지 모른다. 적절한 두께로, 김밥의 결을 따라 자르는 게 핵심.
splitter 는 김밥 종류(=문서 종류)에 따라 절단 방식을 바꾸는 도구다:
  • recursive = "그냥 일정 두께(예: 1cm)로 자름" — 어떤 김밥이든 통용
  • row = "초밥 1피스 단위" — 이미 한 입 크기로 만들어진 경우(엑셀 행)
  • heading = "재료 색깔 바뀌는 지점에서 자름" — 마크다운 헤딩 단위
  • clause = "단무지 위치 기준" — 사규의 "제N조" 위치를 경계로 자름

왜 4종이나 필요한가

청크 경계가 어디에 떨어지냐로 retrieval 품질이 결정된다. 사례:

문서 종류 잘못된 splitter 결과
사규 (제1조 ~ 제48조) recursive 500자 "제39조 휴가 조항" 검색 시 38조 끝~39조 앞부분만 잡혀 정답 못 찾음 (7강 강사 사례)
엑셀 가격표 recursive 1000자 한 청크에 5~7개 행 섞임 → "A제품 가격" 질의에 B/C/D 가격도 노이즈로 옴
정돈된 마크다운 문서 recursive 1500자 섹션 경계를 가로질러 잘림 → "## 보안" 섹션 내용이 두 청크로 쪼개져 일관성↓
핵심. 정답이 들어 있는 청크가 검색 top-k 에 안 들어오면 LLM 이 아무리 똑똑해도 답 못 한다. 청킹은 retrieval 의 recall ceiling 을 정한다.

왜 heading/clause 는 자동선택 안 했나

backend/chat/ingest/splitters/__init__.py 를 보면 DEFAULT_BY_SOURCE dict 가 확장자(csv/pdf/md/…) → splitter 를 매핑하는데, heading/clause 는 일부러 거기서 뺐다.

주의 — 자동선택의 함정.
"md 면 무조건 heading splitter 쓰자" 라고 자동화하면, heading 이 없는 flat markdown (README 줄글) 에서는 splitter 가 한 덩어리만 만들고 끝낸다. 청킹이 사실상 안 일어남.
"pdf 면 무조건 clause" 도 마찬가지. 사규가 아닌 보고서 PDF 에 `제N조` 가 없으면 splitter 가 빈 결과를 낸다.
구조를 가정하는 splitter 는 사용자가 의도적으로 골랐을 때만 안전하다.

그래서 코드 디자인은: - DEFAULT_BY_SOURCE — "확장자만 보고 안전하게 자동 선택" → recursive/row 2종만 - _BY_NAME — "이름으로 명시 호출" → 4종 모두 (opt-in) - frontend chunk_lab.py 의 selectbox = opt-in 통로

T2 임무는 정확히 이 opt-in 통로를 frontend 에 뚫는 일이었다.

1줄 패치였는데 왜 임무로 분리됐나

backend/docs/sessions/2026-05-27-night-parallel.md §7.4 에 분리 사유가 있다 — 수직 격리 규칙. T1 은 moderation(backend), T2 는 frontend chunk_lab, T3 은 docs 만 손댄다. 1줄짜리라도 frontend 영역이 다른 터미널과 섞이면 야간 병렬 commit 시 충돌. 그래서 "frontend 단독" 으로 도려낸 임무가 됐다.
