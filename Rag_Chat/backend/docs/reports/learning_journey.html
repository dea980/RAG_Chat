1RAG 가 뭐예요?

RAG 는 Retrieval-Augmented Generation — 한국어로 "검색으로 보강된 답변 생성". 길지만 풀어보면 단순합니다.

RAG 챗봇 = 도서관 사서. 손님이 "갤럭시 S25 카메라 사양 알려줘" 라고 물으면 사서가 ①책장에서 관련 페이지를 찾아 (Retrieval) ②그 페이지를 보면서 답한다 (Generation). 책 내용을 외워서 답하는 게 아니라, 그때그때 찾아 본다는 게 핵심.

왜 "그때그때 찾아 본다" 가 필요할까요? 다음 섹션이 답을 줍니다.

2LLM 의 한계 — 왜 RAG 가 필요한가

ChatGPT 같은 LLM (Large Language Model, 큰 언어 모델) 은 학습된 텍스트를 기반으로 답합니다. 세 가지 본질적 한계가 있어요:

한계설명RAG 가 푸는 방법
1. 할루시네이션 모르는 걸 그럴듯하게 지어냄 관련 문서를 컨텍스트로 강제 주입 → "이 문서 안에서 찾아 답해"
2. 지식 단절 학습 cutoff 이후 정보 모름 (예: 2024 출시 신제품) 최신 사내 문서를 외부에서 주입
3. 컨텍스트 윈도우 제약 한 번에 처리 가능한 토큰 수 한도 — 사규 100 페이지를 통째로 못 넣음 관련 부분만 잘라서 (chunking) 검색해서 넣음
3번 한계가 RAG 의 진짜 이유. 문서가 컨텍스트 윈도우보다 크니까 *전체를 못 넣음* → *관련 부분만 넣자* → *어떻게 "관련 부분" 을 찾지?* → 검색 = RAG.

토큰 (Token) — 컨텍스트 윈도우의 단위

LLM 은 글자가 아니라 "토큰" 단위로 텍스트를 봅니다. 단어 하나가 될 수도, 단어의 일부가 될 수도 있어요.

토큰 = 레고 블록. 같은 의미라도 한국어는 블록 수가 많고 영어는 적어요. "안녕하세요" = 2~3 토큰, "hello" = 1 토큰. 그래서 같은 컨텍스트 윈도우에 한국어가 정보를 덜 담을 수 있음 — 한국어 비효율.

우리 프로젝트의 Token Lab 페이지 (frontend/pages/token_lab.py) 에서 직접 확인할 수 있어요. 한 문장을 한국어 / 영어 / 일본어로 넣어보면 tokens_per_character 비율이 다르게 나옵니다.

임베딩 (Embedding) — "의미" 를 숫자로

검색이 가능하려면 "의미가 비슷한 것" 을 컴퓨터가 알아야 합니다. 그러려면 텍스트를 숫자로 바꿔야 해요.

임베딩 = GPS 좌표. 모든 단어를 의미 공간의 좌표로 변환. "사과" 와 "배" 는 가깝고, "사과" 와 "자동차" 는 멀어요. 검색 = 질문도 좌표로 바꿔서 가장 가까운 점들 찾기.

벡터 공간의 거리를 재는 게 코사인 유사도. 1 에 가까울수록 비슷, 0 에 가까울수록 다름.

💡 그런데 — "모델마다" 다른 좌표계

여기서 함정. 모델마다 의미 공간이 다릅니다. text-embedding-004 의 좌표와 bge-m3 의 좌표는 완전 별개 — 같은 단어인데 다른 위치.

한국어 약점 — 영어 중심으로 학습된 모델은 한국어 의미를 덜 잘 잡습니다. "연차" 와 "휴가" 가 영어로 학습된 모델에선 멀리 떨어진 점으로 보일 수 있어요. 7강 강사가 39조 못 찾던 사례가 정확히 이 문제.

그래서 모델 선택이 RAG 정확도의 천장. 모델을 손으로 비교할 도구가 필요한데, 그게 다음 작업 — Embedding Lab (설계 단계, design.md). 같은 문장 쌍을 여러 모델로 비교해서 어느 모델이 한국어 의미를 잘 잡는지 한눈에 봅니다.

주의: 모델을 한 번 바꾸면 Chroma 통째로 재인덱싱 필수. 다른 좌표계라 옛 데이터와 비교 불가능. 그래서 미리 검증하는 도구가 가치.

3데이터를 어떻게 "검색 가능" 하게 만드나

대부분의 RAG 튜토리얼은 "이미 텍스트가 준비된 상태" 에서 시작해요. 그런데 현실은 그렇지 않아요. 사내 데이터는 PDF, 한글(HWP), 엑셀, CAD, 스캔 이미지 같은 다양한 포맷.

강의 7강의 데이터 4분류

분류예시처리법이 프로젝트의 상태
1. 텍스트 추출형 PDF, DOCX, HTML, TXT 그대로 텍스트 추출 ✅ 오늘 완료
2. OCR 필요형 스캔 PDF, 이미지 OCR 로 글자 인식 → 분류 1 처럼 처리 ⏳ 다음 단계
3. 구조화 데이터 CSV, Excel, DB RAG 보다 SQL 조회가 더 맞음 일부 (CSV/XLSX), 8강에서 정리
4. 전용 포맷 HWP, CAD, 오디오 포맷별 전용 변환 ⏳ 추후
분류 3 (표 데이터) 가 함정. "작년 4분기 매출" 같은 질문은 의미 검색이 아니라 SQL 쿼리가 정답이에요. 무리하게 RAG 화하면 답변 정확도가 떨어집니다. 이 프로젝트도 galaxy_s25_data.csv 가 현재 RAG 로 강제 처리 중인데, 8강 단계에서 ORM 으로 옮길 예정.

RAG 의 5 단계 흐름

┌─────────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌────────────┐
│  데이터 수집 │ → │  청킹     │ → │  임베딩  │ → │  검색    │ → │  답변 생성 │
│  (인제스천)  │    │ (chunking)│    │(embedding)│    │(retrieval)│    │(generation)│
└─────────────┘    └──────────┘    └──────────┘    └──────────┘    └────────────┘
   [강의 7강의 진짜 1단계]                                          [LLM 호출]

대부분의 튜토리얼이 "청킹" 부터 시작하는데, 강사가 짚은 진짜 1단계는 인제스천 (ingestion). 그래서 이 프로젝트 첫 작업이 인제스천 계층 (Ingest Layer) 부터 만든 거예요.

4오늘의 5단계 — 무엇을 만들었고 무엇을 배웠나

오늘 한 작업을 단계별로 설명할게요. 코드 변경 그 자체보다 왜 그렇게 바꿨는지 에 집중해서 봐주세요.

Step 1 — Skeleton (뼈대) 만들기

문제

처음 코드를 봤을 때 CSV/XLSX 만 처리하는 if/else 가 두 군데에 흩어져 있었어요. PDF 추가하려면? 그 두 군데를 다 수정해야 합니다. 확장성 0.

해결

3개 인터페이스 (Loader / Splitter / Sink) 만 정의하고, 각 포맷 처리기는 플러그인처럼 등록되도록 했어요. 

# chat/ingest/base.py — 표준 인터페이스
@dataclass
class RawDoc:
    content: str             # 검색 대상 텍스트
    source_file: str         # 어디서 왔는지
    source_type: str         # "pdf" | "csv" | "hwp" ...

class BaseLoader:
    def load(self, path) -> Iterable[RawDoc]: ...   # 파일 → RawDoc

class BaseSplitter:
    def split(self, doc) -> Iterable[RawDoc]: ...   # 청크로 쪼개기

class BaseSink:
    def write(self, docs) -> WriteResult: ...       # 저장
USB-C 포트 와 같아요. 충전기·헤드폰·외장디스크 모두 USB-C 하나로 꽂으면 동작. Loader/Splitter/Sink 는 RAG 의 USB-C — 새 포맷 처리기를 꽂으면 (등록하면) 기존 코드 안 바꾸고 동작.

학습 포인트

  • 인터페이스로 분리: PDF loader 가 splitter/sink 를 모르고, splitter 가 loader 를 몰라요. 각 단계가 독립.
  • 플러그인 등록제: @register 데코레이터 하나로 새 loader 가 자동 등록.

Step 2 — Manifest (멱등성) 추가

문제

같은 파일을 두 번 빌드하면 Chroma 벡터 DB 에 중복 적재됐어요. 7행짜리 CSV 가 88 청크로 부풀어 있었습니다.

멱등성 (Idempotency) = 같은 작업을 여러 번 해도 결과가 같음. 운영 안정성의 기본. 깨지면 모든 게 흔들립니다.

해결

두 가지 장치:

  1. SHA256 으로 파일 지문 만들기 — 내용이 바뀌면 지문도 바뀜.
  2. IngestManifest 라는 "장부" — 어떤 파일이 어떤 지문으로 언제 들어왔는지 기록.
도서관 대출 기록부 같은 거예요. "이 책 이미 대출됐나?" 를 확인. 같은 파일이 또 들어오면 → 장부 확인 → 이미 있음 → skip. 내용이 바뀌면 → 옛 청크 삭제 후 새로 등록 + 옛 기록은 SUPERSEDED 표시. 
# 동작 흐름 (간단 버전)
def ingest_path(path):
    sha = sha256(파일_내용)
    if manifest.이미_있나(uri, sha):
        return 0  # skip — 중복 차단
    if 옛_버전_있나(uri):
        sink.delete_ids(옛_청크_id들)
        manifest.SUPERSEDED 표시
    chunks = loader → splitter → sink.write()
    manifest.record_success(uri, sha, chunks)

학습 포인트

  • 결정론적 ID: 청크 id 를 "파일 + 위치 + 내용" 의 해시로 만들면 같은 청크는 항상 같은 id. Chroma 의 add 가 자동으로 upsert 처럼 동작.
  • 운영 안정성이 비동기보다 먼저: 멱등성 없이 Celery 같은 큐 깔면 문제만 가립니다.

Step 3 — Lab 페이지 (학습 도구)

문제

청크 크기를 200 vs 500 vs 1000 으로 바꿔보고 싶은데, 매번 코드 수정하고 재실행하면 너무 느려요.

해결

두 개의 Streamlit 페이지:

  • Chunk Lab — 같은 텍스트를 여러 chunk_size 로 동시에 쪼개서 결과 비교
  • Token Lab — 같은 텍스트가 모델별로 몇 토큰인지 비교 (다른 agent 가 만듦)
핵심 — 이 두 페이지는 저장도 임베딩도 안 함. 결과를 보여주기만 함. 그래서:
  • API key 불필요 → 사내 기밀 문서도 안전
  • 실수해도 운영 DB 오염 X
  • 빠르게 반복 실험

강의 7강 강사가 "200/500/1000 자로 손으로 바꿔가며 비교" 한 그 작업을 한 화면에서 동시에 볼 수 있어요. 사규 39조 못 찾던 사례도 직접 재현 가능.

Step 4 — 통합 (모든 경로가 같은 길로)

문제

하루 동안 여러 agent 가 코드를 추가했어요. PDF/DOCX/HTML loader 가 들어왔고 업로드 API 도 생겼는데, 각자 다른 방식으로 Chroma 에 적재.

  • build_vectors (CLI) — RowSplitter 하드코딩 → PDF 청킹이 안 됨
  • Upload API — manifest 안 거침 → 중복 적재 위험

해결

모든 진입점이 pipeline.ingest_path 한 곳을 거치게 통일. splitter 는 source_type 보고 자동 선택 (csv→row, pdf→recursive 등). 

# build_vectors.py
- splitter = RowSplitter()  # 하드코딩
- ingest_path(path, splitter, sink)
+ ingest_path(path, sink=sink)  # splitter 미지정 → 자동

# Upload API
- chunks = loader.load(); ChromaSink().write(chunks)  # manifest 우회
+ ingest_path(tmp, source_uri_override=f"upload://{name}")  # manifest 통과
경로 통일의 가치 — 한 곳만 잘 만들면 CLI, Upload, 향후 Celery 가 모두 동일하게 멱등성·dedup·로깅 혜택을 받음. "한 곳에서 잘 한다" 가 software engineering 의 핵심 원리.

Step 5 — Phase 4 (opt-in 정책)

문제

Codex 가 두 개의 새 splitter 를 추가했어요:

  • ClauseSplitter: 사규 "제 N 조" 단위로 자르기
  • HeadingSplitter: Markdown heading (#, ##) 단위로 자르기

근데 PDF 가 들어오면 이걸 자동으로 쓸까요? 사규 PDF 면 ClauseSplitter 가 맞지만, 일반 보고서 PDF 면 오히려 망가집니다.

해결 — opt-in only

자동 선택 매핑(DEFAULT_BY_SOURCE) 에는 등록 안 함. 사용자가 명시적으로 호출할 때만 사용 가능. 

# 자동 매핑 — 안전한 default 만
DEFAULT_BY_SOURCE = {
  "pdf": "recursive",   # 일반 PDF → 길이 기반 (안전)
  "html": "recursive",
  ...
}

# clause/heading 은 명시 호출 전용
splitter = splitter_by_name("clause")   # 사용자가 의도적으로 선택
자동차 스포츠 모드 같은 거예요. 기본은 일반 모드 (안전). 운전자가 스포츠 모드를 누를 때만 전환. "사규 문서다" 라는 지식은 사용자에게 있으니까, 그 결정도 사용자가 명시.

학습 포인트

  • 안전한 default + 강력한 opt-in: 자동화는 안전한 것만, 위험한 건 명시 호출. UX 설계의 기본 원리.
  • 확장자만으론 모자라는 정보: 같은 .pdf 라도 사규일 수도, 보고서일 수도 있음. 인간 판단이 필요한 영역은 자동화 안 함.

5손으로 해보기 (실습)

읽기만 하면 안 잡혀요. 다음을 직접 해보세요.

실습 1 · Chunk Lab 으로 청크 크기 비교

  1. cd Rag_Chat && docker compose up -d
  2. http://localhost:8501 → 사이드바 chunk_lab 선택
  3. 아무 한국어 텍스트 (예: 위키백과 첫 문단) 를 붙여넣고
  4. 3개 컬럼에 chunk_size = 100 / 500 / 1000 설정
  5. 관찰: 100 자 → 청크 많고 짧음 / 1000 자 → 청크 적고 김

왜 중요한가: 청크 크기가 retrieval 정확도에 직접 영향. 너무 작으면 맥락 끊김, 너무 크면 노이즈.

실습 2 · Token Lab 으로 한국어 비효율 체감

  1. 같은 화면에서 token_lab 선택
  2. 같은 의미의 문장을 한국어 / 영어로 따로 넣어보기
  3. 관찰: tokens_per_character 가 한국어가 훨씬 높음

왜 중요한가: 같은 컨텍스트 윈도우에 한국어가 정보를 덜 담음 → 한국어 RAG 는 청크 사이즈와 윈도우를 더 신중하게.

실습 3 · 같은 파일 두 번 ingest 해보기 (멱등성 확인)

  1. 터미널에서 cd Rag_Chat/backend
  2. ./venv/bin/python manage.py build_vectors (API key 필요)
  3. 다시 한 번 같은 명령
  4. 관찰: 로그에 skip (already ingested) 가 뜨고 Chroma 청크 수는 변하지 않음

왜 중요한가: 중복 적재 방지가 운영에서 가장 흔히 무너지는 곳. 이게 잡혀야 그 위의 자동화가 안전.

실습 4 · PDF 업로드 → 청크 확인

  1. 아무 짧은 PDF (사규나 매뉴얼 한 페이지) 준비
  2. Chunk Lab 에서 업로드 (저장 없음)
  3. splitter recursive 로 chunk_size 500 → 청크 보기
  4. 한국 사규처럼 "제 N 조" 가 있다면, 다음 단계에서 clause splitter 옵션이 chunk_lab UI 에 추가될 예정 (다음 세션 작업)

왜 중요한가: 문서 종류에 맞는 splitter 선택이 retrieval 정확도를 좌우.

실습 5 · Embedding Lab 으로 모델 비교 (구현 예정)

아직 구현 전 — 설계만 (design.md). 구현되면 다음을 해볼 수 있어요:

  1. 같은 의미인 두 문장 입력 — 예: "연차 휴가가 며칠인가요" vs "연차 사용 가능 일수"
  2. 모델 3개 선택 — gemini / bge-m3 / multilingual-e5
  3. 관찰: 모델마다 유사도 값이 다름. 한국어 약한 모델은 두 문장을 멀게 봄
  4. 의미가 반대인 쌍도 시도 — "월급 인상" vs "임금 삭감" — 좋은 모델은 거리가 멀게 나옴

왜 중요한가: 7강 강사가 임베딩 모델 바꾸고 39조 찾은 그 결정의 근거를 직접 만들 수 있게 됨. 모델 선택이 RAG 의 천장.

6자주 헷갈리는 것 정리

혼동정리
"검색" 과 "생성" 의 관계? 검색이 먼저. 검색 결과를 LLM 컨텍스트에 넣어서 LLM 이 답변 생성. LLM 단독은 RAG 아님.
"청크" 와 "토큰" 은 다른가? 다름. 청크는 문서를 자른 단위 (수백 자), 토큰은 모델이 보는 가장 작은 단위 (~글자/단어 조각).
임베딩 모델 바꾸면 왜 재인덱싱? 모델마다 의미 공간이 달라요. 다른 좌표계 사이에선 거리 계산이 무의미 → 다 새로 만들어야 함.
왜 같은 텍스트인데 매번 다른 답? LLM 의 temperature 파라미터 때문. 0 에 가까우면 결정적, 높으면 창의적. RAG 답변은 보통 낮게.
Chunk Lab 과 운영 ingest 의 차이? Chunk Lab = 저장 X, 청크 모양만 보여줌. 운영 ingest = 임베딩 + Chroma 저장 + manifest 기록.
왜 분류 3 (표) 는 SQL? "512GB 가격" 같은 질문은 정확 조회. 유사도 검색은 노이즈만 늘림. 표는 그냥 WHERE 가 답.

  2. 임베딩의 본질 — 의미의 GPS 좌표화, 코사인 유사도
  3. 청크 크기 트레이드오프 — 작으면 맥락 끊김, 크면 노이즈
  4. 한국어 토큰 비효율 — 같은 의미가 더 많은 토큰 → 윈도우·비용
