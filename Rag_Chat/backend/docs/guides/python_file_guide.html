Rag_Chat Python File Guide

각 Python 파일이 왜 필요한지, 그리고 요청·RAG·ingest·세션 흐름이 어떻게 연결되는지 한 화면에서 보기 위한 문서. 기준 시점: 현재 워크트리의 Django/Streamlit 구조.

빠른 결론
이 프로젝트의 중심축은 frontend/app.py → chat/views.py → chat/pipeline/* → chat/providers/manager.py → Chroma/LLM 이다. 데이터 적재는 build_vectors.py → chat/ingest/pipeline.py → IngestManifest + ChromaSink 로 분리됐다. 토큰 비교는 frontend/pages/token_lab.py → chat/token_views.py → chat/token_utils.py 로 연결된다.

1. 큰 구조

frontend Streamlit 사용자 화면 사용자 생성, 세션 갱신, provider 조합 선택, 채팅 요청 전송을 담당한다.
backend Django REST API 채팅, 검색 로그, health, knowledge 조회, moderation/audit 기록을 제공한다.
rag RAG Pipeline retrieve → rerank → reasoning → generation 순서로 답변을 만든다.
ingest 데이터 적재 계층 파일을 RawDoc 으로 표준화하고, manifest 로 중복을 막고, Chroma 에 기록한다.
infra Redis / Celery / DB Redis 는 세션·대화 history·provider override 에 쓰이고, Celery 는 세션 만료 작업 기반이다.
ops Admin / Audit / Moderation 관리자 페이지, 금지어 필터, API 감사 로그로 운영 안전성을 보강한다.

4. 처음 읽는 순서

  1. frontend/app.py 에서 사용자가 어떤 payload 를 보내는지 확인한다.
  2. chat/urls.py 와 chat/views.py 로 endpoint 를 따라간다.
  3. chat/pipeline/modules.py 와 chat/pipeline/runner.py 로 RAG 실행 순서를 본다.
  4. chat/providers/manager.py 로 어떤 embedding/LLM/vector store 가 실제 생성되는지 본다.
  5. 데이터 적재는 chat/management/commands/build_vectors.py 에서 시작해 chat/ingest/pipeline.py 로 내려간다.
  6. 운영 안정성은 moderation/filter.py, audit/middleware.py, chat/health.py 를 확인한다.
