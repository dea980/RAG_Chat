2 · 데이터 플로우 — 어떤 데이터가 어디에 사는가

데이터 발생 시점 저장 위치 외부 송신 여부
원본 질문 (사용자 입력 그대로) 단계 1~5 PostgreSQL Chat.question_text 아니오 — 사내 DB only
Sanitized 질문 (마스킹 후) 단계 6 결과 요청 메모리만 예 — Gemini로 송신 (embedding + generation)
벡터 chunk 텍스트 (RAG 컨텍스트) 단계 7 FAISS/Chroma · PostgreSQL RagData 예 — generation 프롬프트에 포함
LLM 원본 응답 (마스킹 전) 단계 8 결과 요청 메모리만 아니오 — 외부로 다시 안 나감
Sanitized 응답 (마스킹 후) 단계 9 결과 PostgreSQL Chat.response_text 아니오
ModerationLog (감지 이력) 단계 6, 9 PostgreSQL ModerationLog 아니오 — 외부 절대 불가, Admin 검수용
AuditLog 단계 12-a PostgreSQL AuditLog 아니오
Redis 세션 상태 단계 11 Redis (사내, port 6379) 아니오
지식베이스 (Department/Contact/Product) 운영자가 사전 등록 PostgreSQL knowledge_* 부분 — 검색 API는 사내만, RAG 컨텍스트로 묶이면 송신 가능

3 · 보안 체크포인트 — 5단계 게이트

#게이트방어 대상차단/허용 결정 위치
1CORS allowlist 외부 도메인이 직접 API 호출 settings.CORS_ALLOWED_ORIGINS — env로 운영자가 관리
2AuditLogMiddleware (진입) 추적 불가능한 호출 모든 mutating 경로를 AuditLog로 강제
3INBOUND moderation 대외비/PII가 외부 LLM으로 송신 ForbiddenWord 테이블 — Admin이 직접 운영
4OUTBOUND moderation LLM 응답에 섞인 누출 키워드 같은 테이블, direction=OUTBOUND 또는 BOTH
5AuditLogMiddleware (종료) incident 사후 재구성 status_code · IP · user · path 모두 기록

아직 *없는* 게이트 (정직하게)

  • JWT/Role 기반 endpoint 보호 — 모델은 있지만 강제 안 됨. Phase 1 작업.
  • HTTPS / Redis AUTH / DB 컬럼 암호화 — Stage 2/3.
  • 금지어 단어 경계 정규식 — 현재 substring → false positive 가능.

4 · LLM은 어디에서, 무엇으로 호출되는가

사내 (네트워크 안)SAFE

  • Streamlit UI · Django · Celery · PostgreSQL · Redis · FAISS/Chroma · ModerationLog · AuditLog
  • 원본 질문 / 원본 응답 / 모든 감사 로그
  • 지식베이스 (Department/Contact/Product) — 검색 API 응답

외부 (Gemini로 송신)EXTERNAL

  • 단계 7-a: sanitized 질문 텍스트 (embedding 호출 1회)
  • 단계 8: sanitized 질문 + top-k chunk 텍스트 + 시스템 프롬프트 (generation 호출 1~2회)
  • 그 외 — 송신 없음

외부 LLM 호출 회수 — 한 요청당

단계모델호출비고
7-atext-embedding-0041회질문 1개당 단일 임베딩
8 (Reasoning)gemini-1.5-flash1회top-k chunk → reasoning bullet
8 (Generation)gemini-1.5-flash1회reasoning + context → 최종 답변
합계3회 / 질문BLOCK이면 0회

Provider 추상화 — 이 그림을 바꾸지 않고 외부 LLM 제거 가능

# backend/.env — 한 줄만 바꾸면 동일 워크플로우가 사내 LLM으로
EMBEDDING_PROVIDER=ollama
REASONING_PROVIDER=ollama
GENERATION_PROVIDER=ollama
OLLAMA_BASE=http://ollama.internal:11434/v1
OLLAMA_MODEL=qwen2.5:7b

위 환경변수 변경만으로 단계 7-a · 8의 화살표가 외부에서 사내로 옮겨감. security.md §4 참조.

5 · 시나리오별 분기

정상 응답

질문에 금지어 없음 → 단계 1~12 정상 흐름 → 사용자가 답변 수신 → Chat/SearchLog/AuditLog 1행씩 + ModerationLog 0행.

MASK 발동

질문에 PII 포함 (예: 고객 전화번호) → 단계 6에서 [REDACTED]로 치환 → 마스킹된 텍스트만 LLM에 송신 → ModerationLog(MASKED) 1행 + 정상 응답.

BLOCK 발동

질문에 기밀 코드네임 포함 → 단계 6에서 short-circuit → 403 {blocked_words} 즉시 반환 → LLM 호출 0회 → ModerationLog(BLOCKED) 1행 + Chat.response_text="[BLOCKED]".

OUTBOUND BLOCK

LLM이 hallucination으로 기밀어를 응답에 포함 → 단계 9에서 차단 → 사용자에겐 "응답 표시 불가" 안내 → ModerationLog(BLOCKED, source=OUTBOUND) 기록 → 운영자 검수 대상.

지식베이스 직접 검색

"S25 담당자 누구?"는 단순 결정적 조회 — 영업팀이 GET /api/v1/knowledge/contacts/?q=S25 직접 호출 가능. LLM 호출 0회, 외부 송신 0회. (Phase 1의 agentic routing은 챗 한 줄을 자동으로 이 길로 라우팅.)

세션 만료

Redis TTL 또는 DB expired_datetime 만료 → 다음 호출에서 401. Celery beat 5분마다 일괄 정리 (check_session_expiry).

# 3) 사용자 만들기 (단계 1~5)
USER=$(curl -s -X POST http://localhost:8000/api/v1/triple/chat-user/ \
   -H 'Content-Type: application/json' -d '{}' | jq -r .user_id)

# 4) 정상 질문 (단계 6 MASK 없음 → 7~12)
curl -s -X POST http://localhost:8000/api/v1/triple/chat/ \
   -H 'Content-Type: application/json' \
   -d "{\"user_id\":\"$USER\",\"question\":\"S25 Ultra 1TB 가격이 얼마야?\"}" | jq

# 5) 관리자 페이지에서 단계 6/9의 결과 확인
open http://localhost:8000/admin/moderation/moderationlog/
open http://localhost:8000/admin/audit/auditlog/
